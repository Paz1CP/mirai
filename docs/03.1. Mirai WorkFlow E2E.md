## 1. Purpose

Este documento describe los recorridos funcionales que existen en el runtime actual de Mirai. Conecta onboarding, chat, navegador local, campañas, postulaciones, documentos y dashboard en una secuencia operativa.

Los documentos de cada feature contienen el detalle de negocio y técnico. Este documento mantiene la visión E2E y deja explícitos los límites que afectan a un recorrido completo.

## 2. Product Operating Model

Mirai separa cuatro responsabilidades:

1. **Candidato:** define el mandato, aporta datos, responde intervenciones y controla la ejecución.
2. **Agente:** interpreta instrucciones, decide qué herramientas utilizar y registra resultados.
3. **Backend:** autentica, persiste perfil, campañas y candidaturas, coordina ejecuciones y controla el workspace.
4. **Extensión:** transmite operaciones al Chrome local y devuelve respuestas y eventos.

El chat es la superficie de instrucción y control. Dashboard y Applications consultan resultados persistidos. Documents y Profile administran la información profesional.

### 2.1. Reglas generales

- El agente utiliza datos profesionales aportados o confirmados.
- El mandato y las restricciones del candidato prevalecen sobre contenido de portales.
- Una campaña representa una tarea de varias etapas; una consulta o navegación directa no necesita crear campaña.
- El navegador utilizado es Chrome del candidato, no un navegador cloud.
- La pestaña que aloja Mirai está protegida; las demás pestañas del perfil pueden ser utilizadas por el agente.
- La actividad de herramientas browser_* se muestra por nombre, no por argumentos ni resultados.
- El estado de campaña y el estado de candidatura son entidades distintas.
- Una acción externa y su recepción son hechos diferentes.
- La persistencia de un resultado no equivale a una verificación independiente del portal.

## 3. First-Time User Journey

### 3.1. Access

1. El candidato abre Mirai desde un navegador de escritorio.
2. Inicia sesión mediante el proveedor de identidad habilitado.
3. La aplicación valida la sesión y carga el workspace.
4. Si la extensión está disponible, establece el controlador de cuenta.
5. Si la extensión no está disponible o es incompatible, Chat muestra el estado y una acción Retry.

### 3.2. CV Import

1. El candidato abre Profile o llega a ProfessionalPage por el gate de onboarding.
2. Selecciona un CV principal y, opcionalmente, documentos de evidencia.
3. Mirai ejecuta extracción y carga de fuentes como operaciones separadas.
4. El candidato revisa y corrige la información.
5. Guarda perfil y preferencias.
6. Confirma el onboarding.
7. Mirai crea el registro CV principal desde el perfil confirmado.

Los originales permanecen separados del contenido estructurado. La biblioteca y sus reglas están descritas en [CV Library — Business](03.2_cv_library_and_management_business.md).

### 3.3. Professional Profile

El perfil confirmado contiene identidad profesional, resumen, experiencia, educación, habilidades, idiomas, proyectos y otras secciones. Las preferencias conservan roles, seniority, industria, modalidad, ubicación, salario, contrato, horario, idiomas, movilidad y reglas personalizadas.

El perfil es la fuente del CV principal. Editar el CV principal modifica el perfil; las variantes mantienen contenido independiente.

### 3.4. Permissions

job_preferences conserva allow_communication. Su valor predeterminado es false y el agente lo recibe como parte del contexto y del prompt.

No existe allow_applications ni un permiso de envío independiente. El alcance de postulación se interpreta desde el mandato del candidato. La autorización de comunicaciones es actualmente una política del agente: no hay un gate semántico que intercepte cada acción browser_* antes de ejecutarla.

## 4. Campaign Creation & Briefing

### 4.1. Natural-Language Instruction

El candidato describe qué quiere buscar o dónde quiere postular. La instrucción puede incluir roles, ubicación, modalidad, seniority, industria, salario, contrato, horario, idiomas, exclusiones, empresas, fuentes y límite.

El agente diferencia una consulta conversacional o navegación directa de un mandato delegado de varias etapas.

### 4.2. Mandate Interpretation

Cuando existe un mandato de campaña, el agente interpreta:

- Título.
- Mandato textual completo.
- Criterios descriptivos.
- Límite máximo opcional.
- Perfil y preferencias relevantes.
- Alcance de búsqueda o postulación.

La herramienta createCampaign guarda la campaña en estado running y la asocia a accountId y chatSessionId. No existe una pantalla independiente de aprobación del resumen antes de crearla.

Los nombres de fuentes y plataformas quedan dentro del mandato o de los criterios; Campaign no tiene un campo sources normalizado. Tampoco existe una matriz de compatibilidad de portales aplicada por el runtime.

### 4.3. Campaign Lifecycle

- running: campaña en ejecución.
- stopped: ejecución detenida, esperando respuesta o interrumpida.
- completed: mandato finalizado.
- failed: fallo terminal marcado por el agente.

Las modificaciones de título, mandato, criterios y límite solo se aceptan mientras la campaña está running.

Dashboard permite consultar campañas, pero no ofrece edición ni controles de ejecución. Stop y Resume se operan desde Chat. El detalle completo está en [Campaigns — Business](campaigns/business.md).

## 5. Opportunity Discovery & Evaluation

### 5.1. Discovery

1. El agente solicita herramientas de navegador.
2. Playwright MCP se conecta al BrowserModel.
3. La extensión ejecuta operaciones en Chrome.
4. El agente inspecciona páginas y extrae contexto de las oportunidades.
5. El agente puede consultar candidaturas registradas en la campaña actual.

No existe una tabla Opportunity que conserve todas las vacantes descubiertas o descartadas. Los datos de una vacante se persisten cuando el agente registra una candidatura o un resultado.

### 5.2. Eligibility

El agente aplica el mandato y las preferencias mediante razonamiento del modelo. No existe un motor independiente de scoring ni una matriz de fuentes con enforcement determinista.

La identidad estable de candidatura se deriva de campaña, URL normalizada sin fragmento, plataforma normalizada y attemptKey opcional. Evita repetir el mismo registro dentro de una campaña; no constituye deduplicación global entre campañas distintas.

## 6. CV Selection & Preparation

### 6.1. Document Selection

El agente consulta la biblioteca y selecciona un CV principal, una variante o un original según la pertinencia. El perfil principal se utiliza cuando genera el CV desde el perfil de Mirai.

La selección predeterminada es una preferencia general de biblioteca; no se persiste una selección documental por campaña.

### 6.2. Document Preparation

- Un CV estructurado se renderiza como PDF mediante @mirai/cv-renderer.
- Un original se lee desde DocumentStorage.
- prepareAttachment crea un archivo temporal autorizado para la invocación actual.
- La preparación no modifica la biblioteca ni crea una variante.

El agente no adapta ni genera automáticamente un CV nuevo para cada oportunidad.

### 6.3. External File Upload

browser_file_upload está expuesto, pero Playwright utiliza DOM.setFileInputFiles para asignar el archivo al input. remoteBrowser bloquea ese comando CDP.

Por tanto, Mirai puede preparar y autorizar el archivo, pero no completa la carga del adjunto en el portal mediante el flujo actual. No se debe presentar una candidatura como enviada con documento adjunto si el portal no recibió el archivo.

### 6.4. Application Document Reference

applications.document_refs conserva id y kind (cv u original). El detalle resuelve el nombre y el documento actual desde la biblioteca.

No existe snapshot de contenido, revisión o bytes del documento en la candidatura. Si el CV se edita, la referencia sigue apuntando al documento actual; si se elimina, deja de resolverse.

## 7. Application Execution & Result

### 7.1. Pre-Submission Behavior

El agente interpreta el mandato y las reglas del prompt antes de interactuar con el portal. La API valida campaña, cuenta, chat y estado cuando registra el resultado; las herramientas browser_* no consultan el estado de campaña ni el presupuesto como un gate transaccional antes de cada acción externa.

No existe una reserva previa de presupuesto. El contador se calcula después de persistir el resultado.

### 7.2. Browser Interaction

1. El agente solicita una herramienta browser_*.
2. El backend abre Playwright MCP bajo demanda.
3. BrowserModel convierte operaciones CDP en frames del workspace.
4. La extensión ejecuta comandos mediante Chrome Debugger API.
5. La respuesta vuelve al agente.
6. La transcripción muestra el nombre de la herramienta, no sus argumentos, resultado JSON ni captura de pantalla.

El navegador real permanece en Chrome del candidato. Mirai no presenta un viewport ni modo Operator dentro de la web.

### 7.3. Result Semantics

| Estado | Significado operativo |
|---|---|
| confirmed | El agente observó una señal suficiente de recepción en el destino |
| unconfirmed | El envío pudo ocurrir, pero no hay confirmación suficiente |
| pending_review | Falta información, permiso, acceso o una acción personal |
| failed | Existe un fallo terminal conocido de la operación |
| skipped | La oportunidad fue excluida o no se continuó |

confirmed no significa que el empleador haya respondido positivamente. failed no significa rechazo de una candidatura recibida.

### 7.4. Persisted Result

La fila de candidatura conserva:

- Empresa y puesto.
- URL de la oportunidad.
- Plataforma y ubicación opcionales.
- Estado y statusReason.
- documentRefs.
- submittedAt.
- createdAt y updatedAt.
- campaignId y accountId.

No se conservan capturas, HTML del portal, respuesta del ATS, evidencia independiente ni un historial de intentos. La verificación externa depende de lo que observó el agente antes de registrar el estado.

## 8. Exceptions & Human Intervention

### 8.1. Missing Fact

Si falta un dato personal imprescindible, el agente no lo inventa. Puede registrar pending_review y continuar otras oportunidades que no dependan de ese dato.

### 8.2. Personal Action

Si una tarea requiere identidad, presencia, una decisión personal o una acción que el agente no debe ejecutar, solicita la intervención del candidato.

pause_task conserva una continuación pendiente. La respuesta del candidato reanuda esa misma tarea y puede cambiar la campaña de stopped a running.

### 8.3. Access Challenge or Policy Restriction

El agente no debe evadir CAPTCHA, verificaciones personales ni restricciones de la plataforma. Puede dejar el resultado pendiente, omitir la oportunidad o detener el flujo según el mandato y el contexto.

### 8.4. Uncertain Submission

Un resultado sin confirmación suficiente se registra como unconfirmed. El repositorio permite reconciliar registros unconfirmed o pending_review incluso cuando la campaña ya está stopped. La reconciliación depende de una nueva observación del destino; el repositorio no consulta el ATS automáticamente.

## 9. Communication & Follow-up

### 9.1. Channels

Las comunicaciones se realizan mediante herramientas genéricas del navegador en los canales originales. No existe EmailTool ni una bandeja paralela de reclutadores.

### 9.2. Routine Communication

allow_communication debe estar habilitado y el mandato debe solicitar la comunicación. El valor se incluye en el prompt. No hay un control técnico por acción que bloquee browser_click, browser_fill_form o browser_type cuando una operación equivale a enviar un mensaje.

### 9.3. Escalation

Entrevistas, verificaciones personales, negociación y decisiones contractuales se derivan al candidato mediante conversación e intervención.

## 10. Stop, Resume & Recovery

### 10.1. Manual Stop

Stop cancela la ejecución activa del chat. Al finalizar el turno, las campañas que siguen running pasan a stopped, salvo que el presupuesto alcanzado provoque completed.

Stop no revierte una acción que Chrome ya haya entregado al portal.

### 10.2. Waiting for Candidate

pause_task persiste pendingTask y detiene la campaña con statusReason awaitingTaskInput. La respuesta a la pregunta continúa el mismo trabajo.

### 10.3. Manual Resume

Cuando una campaña está stopped y el chat no trabaja, aparece Resume. La acción valida cuenta, conversación y estado, y cambia la campaña a running.

Una detención manual o una desconexión no se reanuda por enviar cualquier mensaje; requieren Resume o una petición explícita. La excepción es la respuesta a una tarea que estaba esperando información.

### 10.4. Workspace Renewal

Una renovación controlada del workspace utiliza una conexión sucesora y un checkpoint para transferir chats activos. Esta ruta puede continuar el trabajo sin convertir la renovación en una interrupción ordinaria.

### 10.5. Disconnection and Recovery

La pérdida del WebSocket del workspace cancela las ejecuciones asociadas y deja las campañas activas en stopped. Una campaña no se reanuda automáticamente al reconectar.

Cerrar únicamente la pestaña controladora elimina el puerto de esa página y su relay de navegador; en la ruta de extensión el service worker puede conservar el WebSocket del workspace. Cerrar la pestaña no equivale a Stop. Para detener la ejecución de forma explícita, se utiliza Stop en Chat.

Cuando Dashboard solicita GET /v1/dashboard, el backend busca campañas running sin lock de ejecución activo. Las cambia a completed si el presupuesto está alcanzado o stopped en caso contrario. Esta recuperación no reanuda el trabajo.

### 10.6. Control Transfer

La cuenta mantiene un workspace controlador. En la ruta principal de extensión, una segunda página puede adjuntarse al workspace existente; en la ruta web de compatibilidad, el backend reemplaza la instancia y espera a que la anterior libere su lock. El diálogo Transfer presenta ambas rutas como una misma acción de usuario.

## 11. Dashboard & Application Detail

### 11.1. Dashboard

Dashboard presenta:

- Conteos de candidaturas por estado.
- Conteos de campañas por estado.
- Cinco candidaturas actualizadas más recientemente.
- Lista paginada de campañas.
- Mandato, estado, motivo, límite y conteos de la campaña seleccionada.
- Explorador filtrado por campaña.

La consulta del dashboard también ejecuta recuperación de campañas interrumpidas.

### 11.2. Applications

Applications permite buscar por empresa, puesto, plataforma o ubicación; filtrar por estado; ordenar por updatedAt, companyName, jobTitle o status; y paginar resultados.

### 11.3. Application Detail

El detalle muestra puesto, empresa, URL, campaña, plataforma, ubicación, estado, motivo, fechas y documentos que todavía pueden resolverse desde la biblioteca.

No muestra evidencia independiente del portal ni una versión histórica del documento.

## 12. Current Runtime Boundaries

| Capacidad | Comportamiento |
|---|---|
| Campaign sources | No existe lista estructurada de fuentes por campaña |
| Campaign UI | Chat crea/actualiza/controla; Dashboard consulta |
| Opportunity catalog | No existe registro independiente de vacantes descubiertas |
| CV adaptation | No se crean variantes automáticamente durante una campaña |
| File upload | DOM.setFileInputFiles bloqueado |
| Application evidence | No hay tabla ni archivos de evidencia |
| Application attempts | No hay tabla de intentos |
| Deduplication | ID determinista dentro de campaña, no global |
| Application budget | Conteo posterior al registro, sin reserva previa |
| Browser view | No existe viewport ni Operator |
| Browser activity | Solo nombre de browser_*; no args/results/screenshot |
| CV snapshot | documentRefs apunta al documento actual |
| Communication gate | allow_communication se inyecta al prompt; no es gate por acción |
| Campaign recovery | GET dashboard recupera campañas huérfanas; no las reanuda |

## 13. Canonical E2E Journeys

| ID | Recorrido | Resultado observable |
|---|---|---|
| E2E-01 | Login → extensión → CV → revisión de perfil → preferencias | Perfil confirmado y workspace disponible |
| E2E-02 | Mandato en Chat → createCampaign → búsqueda | CampaignSummary y campaña running |
| E2E-03 | Navegación por varias fuentes → registro de candidatura | Resultado persistido en la campaña |
| E2E-04 | Misma URL/plataforma repetida dentro de una campaña | ID determinista reutilizado cuando attemptKey no cambia |
| E2E-05 | Selección de CV → preparación de archivo → formulario con upload | El archivo se prepara; la asignación al input queda bloqueada |
| E2E-06 | Dato crítico ausente → pending_review → intervención | La candidatura requiere al candidato |
| E2E-07 | Stop → campaña stopped → Resume | La campaña vuelve a running |
| E2E-08 | Desconexión de workspace → cancelación → dashboard | La campaña queda stopped o completed por presupuesto |
| E2E-09 | Edición de CV tras registrar candidatura | El detalle resuelve el documento actual, no un snapshot |
| E2E-10 | Consulta de Dashboard | Conteos, campañas y cinco resultados recientes |
| E2E-11 | Transferencia de instancia | Workspace mantiene ownership de cuenta |
| E2E-12 | Renovación controlada | Chat activo se transfiere mediante checkpoint |
