## 1. Purpose

Este documento describe el recorrido integral del candidato y el comportamiento esperado de Mirai desde el primer acceso hasta la gestión de campañas y resultados.

El flujo conecta identidad, perfil, CV, permisos, chat, agente, navegador, campañas, candidaturas, comunicaciones y dashboard. Su propósito es mantener una única experiencia coherente, con resultados trazables y control explícito del usuario.

## 2. Product Operating Model

Mirai funciona como un servicio delegado de trabajo digital. El candidato define un mandato; el agente lo interpreta y ejecuta tareas permitidas mediante herramientas de dominio y un navegador de escritorio vinculado.

### 2.1. Principales responsabilidades

| Actor | Responsabilidad |
|---|---|
| Candidato | Aportar información, definir condiciones, autorizar, revisar y resolver intervenciones |
| Web App | Presentar chat, perfil, biblioteca, dashboard, estados y controles |
| Agente | Interpretar mandato, descubrir oportunidades, preparar candidaturas y coordinar tareas |
| Extension | Vincular el navegador local y transmitir operaciones autorizadas |
| API | Validar identidad y permisos, coordinar ejecución y conservar resultados |
| Portales externos | Publicar oportunidades, recibir candidaturas y comunicar respuestas |

### 2.2. Reglas generales de autonomía

- Una campaña autorizada puede buscar, evaluar, preparar, enviar y registrar candidaturas elegibles sin pedir aprobación rutinaria para cada formulario.
- El candidato conserva el control de las restricciones, los permisos, la pausa, la reanudación y las decisiones personales.
- El agente utiliza únicamente hechos declarados o confirmados por el candidato.
- La autorización del usuario no sustituye las condiciones de acceso de un portal.
- Un envío cuenta como confirmado solo cuando existe una señal verificable del destino.
- Una oportunidad pendiente no paraliza el resto de la campaña cuando las demás tareas pueden continuar con seguridad.

## 3. First-Time User Journey

### 3.1. Access

1. El candidato abre Mirai desde un navegador de escritorio compatible.
2. Inicia sesión mediante el proveedor de identidad habilitado.
3. La aplicación valida la sesión y muestra el espacio de trabajo.
4. Mirai solicita conectar la extensión de navegador.
5. El candidato instala o abre la extensión y autoriza la conexión desde el origen de Mirai.
6. La aplicación muestra el estado del workspace: desconectado, conectando, disponible o error.

**Resultado esperado:** cuenta accesible y navegador vinculado, sin iniciar todavía acciones externas.

### 3.2. CV Import

1. El candidato abre Biblioteca de CV.
2. Selecciona un documento PDF o DOCX.
3. Mirai valida el archivo y ejecuta la extracción.
4. La interfaz muestra la información profesional identificada.
5. El candidato revisa, corrige y confirma los datos.
6. El documento original permanece como fuente de referencia.

Los datos desconocidos no se completan por inferencia. Si una candidatura requiere un hecho que no aparece en el perfil, el agente debe solicitarlo al candidato.

### 3.3. Professional Profile

El perfil reúne:

- Identidad y datos de contacto.
- Experiencia profesional.
- Formación y certificaciones.
- Proyectos.
- Habilidades.
- Idiomas.
- Enlaces profesionales.
- Preferencias y restricciones laborales.
- Reglas personalizadas.

Cada preferencia distingue si actúa como restricción obligatoria o como preferencia flexible.

### 3.4. Permissions

El candidato configura permisos por alcance:

- Navegación y operación de sitios laborales.
- Consulta de canales externos.
- Envío de comunicaciones rutinarias.
- Otras acciones que requieran autorización diferenciada.

La autorización puede reutilizarse mientras conserve su vigencia y alcance. La revocación impide nuevas acciones del alcance afectado; no modifica registros históricos ni deshace un envío externo que ya llegó al destino.

## 4. Campaign Creation & Briefing

### 4.1. Natural-Language Instruction

El candidato inicia un chat y describe el trabajo que quiere delegar. La instrucción puede incluir:

- Roles y especializaciones.
- Empresas o fuentes.
- Países, regiones o ciudades.
- Modalidad remota, híbrida o presencial.
- Seniority.
- Industria.
- Salario mínimo, moneda y periodicidad.
- Horario y tipo de contrato.
- Idiomas.
- Movilidad y patrocinio de visa.
- Exclusiones y reglas personalizadas.
- Máximo de candidaturas.

### 4.2. Mandate Interpretation

El agente transforma la instrucción en un resumen estructurado. Antes de iniciar, el candidato debe poder comprender:

1. Qué busca Mirai.
2. Qué fuentes puede consultar.
3. Qué condiciones son obligatorias.
4. Qué preferencias influyen en la evaluación.
5. Qué límite de candidaturas aplica.
6. Qué permisos habilitan acciones externas.
7. Qué situaciones requieren intervención.

Si existe una ambigüedad crítica, el agente pregunta antes de ejecutar la acción afectada. No necesita detener la configuración por detalles que no cambian la elegibilidad o la autorización.

### 4.3. Campaign Lifecycle

| Estado | Presentación al candidato | Comportamiento |
|---|---|---|
| running | En curso | Puede ejecutar tareas autorizadas |
| stopped | Pausada | No inicia nuevas acciones; requiere reanudación explícita |
| completed | Finalizada | El mandato llega a su condición de cierre |
| failed | Fallida | Un error terminal impide continuar con seguridad |

La campaña conserva mandato, criterios, fuentes, límite, conversación de origen y marcas temporales.

## 5. Opportunity Discovery & Evaluation

### 5.1. Discovery

1. El agente consulta las fuentes incluidas en el mandato.
2. Abre páginas y ofertas mediante el navegador autorizado.
3. Captura título, empresa, descripción, ubicación, URL, plataforma y datos necesarios para evaluar.
4. Normaliza la oportunidad para reconocer repeticiones.
5. Registra la fuente de cada dato relevante.

Mirai no presupone que todos los portales son compatibles. Una fuente se considera operable según su flujo y condiciones de uso.

### 5.2. Eligibility

La evaluación sigue este orden:

1. Comprobar si la fuente permite la operación solicitada.
2. Aplicar exclusiones obligatorias.
3. Comprobar requisitos indispensables.
4. Evaluar preferencias flexibles y pertinencia profesional.
5. Comprobar duplicados.
6. Verificar el límite de campaña.
7. Clasificar la oportunidad.

| Resultado de evaluación | Acción |
|---|---|
| Elegible | Preparar candidatura |
| Incompatible con restricción obligatoria | Omitir y explicar el motivo |
| Duplicada | Omitir y vincular el registro existente |
| Fuente no permitida | Detener esa fuente y comunicar la restricción |
| Dato crítico desconocido | Pendiente de revisión |
| Límite alcanzado | No iniciar otra candidatura |

No se utiliza un score decorativo como sustituto de las razones de elegibilidad.

## 6. CV Selection & Preparation

### 6.1. Document Selection

El agente consulta la biblioteca y selecciona el documento que mejor representa el mandato y la oportunidad. El candidato puede definir un CV predeterminado o seleccionar una variante específica.

### 6.2. Adaptation

La adaptación puede reorganizar, resumir o destacar hechos existentes para responder a la oferta. No puede inventar:

- Empleadores.
- Cargos.
- Fechas.
- Años de experiencia.
- Certificaciones.
- Proyectos.
- Resultados o métricas.
- Habilidades no declaradas.

Si el contenido necesita un dato desconocido, el agente pregunta o deja esa candidatura pendiente.

### 6.3. Original, Variant & Version

La biblioteca diferencia:

- **Original:** archivo fuente inmutable.
- **CV principal:** documento de referencia profesional.
- **Variante:** documento derivado para una especialización o tipo de rol.
- **Versión:** snapshot histórico de una variante.

El flujo de edición conserva el documento base, muestra diferencias entre antes y después y permite guardar, descartar o ajustar. Restaurar una versión anterior crea una nueva versión; no elimina el historial.

### 6.4. Application Snapshot

Al registrar una candidatura, Mirai conserva la referencia al documento exacto utilizado. Las ediciones posteriores de la biblioteca no cambian el documento asociado a esa candidatura.

## 7. Application Execution

### 7.1. Pre-Submission Checks

Antes de operar el formulario, el agente verifica:

- Campaña en estado running.
- Permiso de navegación vigente.
- Fuente y flujo permitidos.
- Oportunidad elegible y no duplicada.
- Límite disponible.
- Documento seleccionado y snapshot identificable.
- Datos necesarios disponibles.
- Ausencia de una operación previa incierta que requiera reconciliación.

### 7.2. Browser Interaction

1. El agente abre la oportunidad en una pestaña de trabajo.
2. Revisa el formulario y sus pasos.
3. Completa campos con información del perfil.
4. Selecciona respuestas fundamentadas.
5. Adjunta el documento correcto.
6. Resuelve validaciones ordinarias permitidas.
7. Verifica que los campos obligatorios tengan valores válidos.
8. Comprueba nuevamente los permisos antes de la acción externa.
9. Envía la candidatura.
10. Observa la respuesta del portal y registra el resultado.

La pestaña controladora de Mirai permanece protegida. El candidato puede utilizar el resto de su navegador sin que el agente intercepte su escritura.

### 7.3. Result Semantics

| Estado | Condición | Tratamiento |
|---|---|---|
| confirmed | El destino muestra una confirmación verificable | Cuenta como candidatura enviada |
| unconfirmed | El envío pudo ocurrir, pero la recepción no puede demostrarse | No cuenta como confirmada; requiere reconciliación |
| pending_review | Falta dato, autorización o acción personal | Espera al candidato |
| failed | El destino rechaza la operación o existe un error terminal conocido | Se registra la causa |
| skipped | La oportunidad es incompatible, duplicada o excluida | No se envía |

Un clic, un formulario completo o una respuesta HTTP genérica no constituyen por sí solos evidencia suficiente de recepción.

### 7.4. Evidence & Traceability

El detalle de una candidatura debe permitir responder:

- ¿Qué oportunidad era?
- ¿En qué fuente se encontró?
- ¿Qué campaña la originó?
- ¿Qué documento se utilizó?
- ¿Cuándo ocurrió el intento?
- ¿Qué respuesta entregó el destino?
- ¿Por qué el estado es confirmed, unconfirmed, pending_review, failed o skipped?

La evidencia puede incluir referencia al destino, marca temporal, resumen de confirmación y artefactos permitidos. No se deben conservar credenciales, cookies ni contenido personal innecesario.

## 8. Exceptions & Human Intervention

### 8.1. Missing Fact

Cuando un formulario solicita información que no está en el perfil:

1. El agente identifica el campo y su motivo.
2. Guarda el contexto de la candidatura.
3. Marca esa tarea como pending_review.
4. Pregunta al candidato con una explicación concreta.
5. Permite responder, corregir, omitir o actualizar el perfil.
6. Reanuda la candidatura solo después de validar el dato y el permiso.
7. Continúa con otras oportunidades que no dependan de ese dato.

### 8.2. Personal Action

Las siguientes acciones requieren participación del candidato:

- Entrevistas presenciales o en vivo.
- Video, voz o pruebas de identidad personal.
- Evaluaciones que requieran presencia.
- Negociación personal.
- Aceptación o rechazo de ofertas.
- Firma de contratos.
- Decisiones que comprometan legalmente al candidato.

Mirai registra el pendiente y proporciona el contexto o enlace. No suplanta al candidato.

### 8.3. Access Challenge or Policy Restriction

Cuando un portal exige una verificación que no puede completarse dentro de los permisos o condiciones admitidas, Mirai detiene esa operación y explica el motivo. La existencia de un CAPTCHA o una barrera antiabuso no autoriza a evadirla.

### 8.4. Uncertain Submission

Cuando la conexión se pierde después de una posible acción de envío:

1. El resultado se conserva como unconfirmed.
2. La campaña reserva capacidad para no exceder el límite.
3. La recuperación consulta el destino o solicita revisión.
4. Solo después de reconciliar se permite una nueva acción.
5. Nunca se reenvía a ciegas.

## 9. Communication & Follow-up

### 9.1. Channels

Las comunicaciones se realizan en el canal original autorizado, por ejemplo, una interfaz de portal o Gmail en el navegador del candidato. El producto no crea una bandeja paralela de reclutadores.

### 9.2. Routine Communication

El agente puede responder consultas rutinarias cuando:

- El canal está autorizado.
- La campaña o seguimiento mantiene vigencia.
- La respuesta se fundamenta en información confirmada.
- La comunicación no implica una decisión personal.

### 9.3. Escalation

Una invitación a entrevista, solicitud de disponibilidad personal, negociación salarial, aceptación de oferta o petición de información no disponible se deriva al candidato.

El dashboard conserva una anotación operativa y un enlace al canal original; no sustituye el historial externo de conversación.

## 10. Pause, Resume & Recovery

### 10.1. Manual Pause

Cuando el candidato pausa una campaña:

- Se impide el inicio de nuevas acciones externas.
- Se conserva el estado de la operación actual.
- El chat y el navegador reflejan la pausa.
- Los resultados confirmados permanecen disponibles.
- La reanudación requiere una acción explícita.

### 10.2. Closing the Controller Tab

Cerrar la pestaña controladora detiene nuevas acciones. Al volver, Mirai presenta el estado de la campaña y solicita reanudación explícita.

### 10.3. Browser or Extension Disconnect

Si la extensión pierde conexión:

1. El workspace pasa a estado de error o desconectado.
2. La campaña deja de iniciar operaciones.
3. La interfaz ofrece reconectar.
4. La API conserva el contexto y los resultados registrados.
5. La reconexión valida ownership y permisos.
6. Los envíos inciertos se reconcilian.
7. Una campaña pausada continúa pausada hasta que el candidato la reanude.

### 10.4. Control Transfer

Una cuenta tiene una sola instancia controladora. Si el candidato abre Mirai en otra ventana, navegador o equipo, puede cancelar la nueva conexión o transferir el control. La instancia anterior deja de iniciar operaciones después de la transferencia.

## 11. Campaign Completion & Report

Una campaña puede finalizar cuando:

- El candidato la termina.
- Se alcanza el límite configurado.
- Se cumple la condición de cierre del mandato.
- No quedan oportunidades elegibles dentro del alcance.
- Un error terminal impide continuar.

El reporte separa:

- Candidaturas confirmadas.
- Envíos no confirmados.
- Pendientes de revisión.
- Fallidas.
- Omitidas.
- Fuentes con restricciones o errores.
- Próximas acciones que requieren al candidato.

Solo las confirmadas se contabilizan como enviadas. El reporte debe reflejar resultados verificables, no métricas de actividad cosméticas.

## 12. Dashboard & Application Detail

### 12.1. Dashboard

El dashboard presenta un resumen de campañas y candidaturas. La tabla permite buscar, filtrar, ordenar y paginar. Los estados se muestran mediante texto, icono y descripción; no dependen exclusivamente del color.

### 12.2. Application Detail

El detalle incluye:

- Empresa y puesto.
- Fuente y URL.
- Ubicación.
- Campaña de origen.
- Estado y motivo.
- Fechas relevantes.
- Documento exacto utilizado.
- Evidencia disponible.
- Comunicación o intervención relacionada, cuando corresponda.

El candidato puede regresar al registro desde el detalle sin perder el contexto de la tabla.

## 13. Main Navigation & UI States

La navegación principal contiene cinco áreas:

| Área | Responsabilidad |
|---|---|
| Chat | Mandatos, conversación, actividad y control de ejecución |
| Dashboard | Resumen de resultados y campañas |
| Postulaciones | Lista, filtros y detalle de candidaturas |
| Biblioteca de CV | Originales, variantes, versiones y selección |
| Perfil profesional | Datos, preferencias y permisos |

### 13.1. Chat

Estados principales:

- Nueva conversación.
- Briefing del mandato.
- Búsqueda.
- Preparación y postulación.
- Registro de resultado y continuación.
- Dato faltante.
- Pausa.
- Regreso tras cierre.
- Error de extensión.
- Finalización.
- Operator vacío o trabajando.
- Historial y contexto largo.

### 13.2. Operator

Operator cambia la proporción visual entre chat y navegador. No crea una segunda ejecución ni una segunda campaña. La conversación, documento, operación y contexto permanecen asociados.

### 13.3. CV Library

La biblioteca diferencia documento original, principal y variantes. La vista de revisión muestra diferencias, timeline, comparación, restauración, descarga y confirmación de borrado.

### 13.4. Responsive Scope

El MVP es desktop-first. Las pantallas de referencia utilizan 1440 × 900 y 1600 × 900, con comprobaciones de composición a 1366 × 768. La experiencia móvil no forma parte del flujo de ejecución del navegador.

## 14. Canonical E2E Journeys

Los once recorridos siguientes conectan estados de producto, acciones del candidato y eventos externos. Los destinos visuales y frames se detallan en [UI/UX E2E](design/mirai_ui_ux_e2e.md).

| ID | Recorrido | Secuencia resumida | Invariante |
|---|---|---|---|
| **E2E-01** | Ingreso, CV y primera instrucción | Login → extensión → importar CV → revisar perfil → permisos → chat → briefing | El candidato revisa su información y autoriza antes de ejecutar |
| **E2E-02** | Campaña continua | Briefing → búsqueda → filtros → seleccionar CV → postular → registrar → continuar | Solo oportunidades elegibles llegan al envío |
| **E2E-03** | Confirmación y trazabilidad | Resultado → dashboard → detalle | Una confirmación conserva evidencia y documento identificable |
| **E2E-04** | Dato pendiente sin bloquear | Pregunta → continuar otras oportunidades → responder → actualizar perfil → reanudar | Una pregunta afecta solo la candidatura dependiente |
| **E2E-05** | Original, variante y revisión | Original → duplicar → editar → comparar → guardar versión → seleccionar | El original permanece intacto y las versiones son recuperables |
| **E2E-06** | Pausar y reanudar | Ejecución → pausa → estado detenido → reanudación explícita | No comienzan nuevas acciones mientras la campaña está pausada |
| **E2E-07** | Cerrar y volver | Ejecución → aviso de cierre → cerrar → volver → reanudar | Cerrar detiene nuevas acciones y no reanuda por sí solo |
| **E2E-08** | Control exclusivo entre ventanas | Segunda instancia → transferir control → instancia anterior pierde autoridad | Una sola instancia controla la cuenta |
| **E2E-09** | Finalización y reporte | Notificación → chat finalizado → dashboard | Solo confirmed cuenta como enviado |
| **E2E-10** | Comunicación en canal original | Permisos → canal externo → respuesta rutinaria → anotación | Permiso reutilizable y canal original; sin inbox propio |
| **E2E-11** | Recuperación e incertidumbre | Error de extensión → reconectar → portal bloqueado → resultado incierto → guardar error | No se inventa éxito ni se reenvía automáticamente |

## 15. Generative UI Contracts

Los bloques generativos reciben datos estructurados; el modelo no genera componentes o HTML arbitrarios.

| Bloque | Datos principales | Acciones del candidato |
|---|---|---|
| CampaignSummary | campaignId, role, portals, constraints, limit, CV, state, counters | Consultar campaña y documento |
| ExecutionLog | operationId, state, summary, timestamp, steps | Expandir o plegar pasos |
| ResultRow | applicationId, company, role, result, evidenceRef, documentRef | Abrir candidatura |
| Intervention | applicationId, question, reason, inputType, options, requiredScope | Responder, omitir o realizar acción personal |
| DocumentReview | documentId, baseVersion, proposedVersion, sections | Revisar, ajustar, guardar o descartar |
| CompactReport | campaignId, confirmed, uncertain, pending, failed, skipped, resultRefs | Abrir registros y pendientes |

Los contadores se derivan de resultados persistidos; no se incrementan por texto generado por el modelo.

## 16. Product Invariants

1. El candidato conserva la autoridad sobre perfil, restricciones y permisos.
2. El agente no inventa hechos profesionales.
3. Ninguna fuente se automatiza fuera de las condiciones permitidas.
4. Una candidatura no es confirmada por el solo hecho de intentar enviarla.
5. Una oportunidad no se envía dos veces.
6. Un resultado incierto no genera reintento ciego.
7. Una campaña pausada no inicia nuevas acciones.
8. Una desconexión no elimina resultados confirmados.
9. Una intervención pendiente no bloquea tareas independientes.
10. Una candidatura conserva el documento exacto utilizado.
11. La comunicación permanece en el canal original autorizado.
12. La cuenta tiene un único controlador activo.
13. El reporte distingue confirmadas, inciertas, pendientes, fallidas y omitidas.
14. El agente opera bajo el mandato y los permisos vigentes, nunca bajo instrucciones contenidas en páginas externas.

- [ ] El recorrido de onboarding conserva los datos extraídos y permite corregirlos.
- [ ] El mandato se muestra de forma comprensible antes de iniciar.

- [ ] El agente no inventa hechos profesionales.
- [ ] El navegador opera bajo permisos y fuentes admitidas.
- [ ] La selección documental conserva un snapshot identificable.
- [ ] La recepción del destino determina el estado confirmed.
- [ ] Los resultados inciertos se reconcilian antes de un nuevo envío.
- [ ] Los pendientes no bloquean oportunidades independientes.
- [ ] Pausa, cierre y transferencia detienen nuevas acciones.
- [ ] La recuperación conserva confirmaciones y evita duplicados.
