## 0. Decisiones y criterios de arquitectura

| Área | Diseño elegido | Función |
|---|---|---|
| Web | Next.js App Router, React, TypeScript, Tailwind | Experiencia de candidato; vista y control de campaña |
| Datos de UI | TanStack Query; Zustand únicamente para estado efímero | Datos del servidor, conexión local y preferencias de vista |
| Validación | Zod | Validación de contratos y datos extraídos; formularios clásicos mínimos |
| API | Node.js + Express, REST/OpenAPI | Autorizar, persistir, coordinar e invocar IA |
| Extensión | TypeScript + WXT + WebExtensions API | Navegación en el dispositivo, pestañas propias, ejecución de acciones |
| Datos | Neon PostgreSQL + Drizzle ORM + Drizzle Kit | Estado transaccional, campañas, intentos y auditoría |
| Archivos | Neon Object Storage privado | CV originales, versiones y documentos temporales |
| Identidad | Neon Auth (Managed Better Auth) + Google OAuth | Inicio de sesión con Google, usuarios y sesiones administrados |
| IA | Adaptador del servidor hacia Vertex AI / modelos compatibles | Interpretación, planificación, generación y Computer Use; Gemini 4 Carbon es candidato |
| Hosting | Google Cloud Run: servicio `web` y servicio `api` | Despliegues separados y escalado a cero |
| Calidad | Vitest | Pruebas iniciales de reglas, estados, contratos y adaptadores simulados |
| Instrumentación | PostHog | Eventos de producto y métricas técnicas estructuradas, sin datos sensibles |
| Distribución | Docker + GitHub Actions | Builds y despliegues |

**Restricciones:** no ejecutar navegadores en la nube por usuario; no base de datos de vacantes como producto; no porcentaje de match; no límite artificial de candidaturas elegibles, respetando el máximo que indique el candidato; no dependencia de API de los portales; no worker autónomo que siga postulando tras cerrar la pestaña de la aplicación. El pago habilita el servicio, pero proveedor, precio y periodicidad son configurables.

**Atributos prioritarios (ISO/IEC/IEEE 42010):** seguridad de la autorización, integridad de los envíos, recuperación verificable, aislamiento entre usuarios, compatibilidad de navegadores, bajo costo inactivo y sustituibilidad del modelo. La arquitectura se valora contra estos criterios, no por el número de componentes.

## 1. Domain Modeling & Analysis Class Modeling

### 1.1. Subdominios y responsables

| Contexto | Agregado principal | Responsabilidad / frontera |
|---|---|---|
| Identidad y acceso | `Account` | Titularidad, credenciales delegadas, dispositivos y derecho de uso |
| Perfil profesional | `CandidateProfile` | CV original, biblioteca de variantes, hechos declarados y versiones |
| Mandato de búsqueda | `Campaign` | Restricciones duras, preferencias, permisos, ejecución habilitada |
| Oportunidades y postulaciones | `Application` | Oportunidad observada, evaluación, intento, evidencia, resultado |
| Comunicaciones externas | `OutboundIntent` | Acciones autorizadas en portales o correo y prevención de envíos duplicados |
| Ejecución del agente | `AgentRun` | Pasos, control de pestaña, costo, checkpoints, recuperación |
| Facturación | `Entitlement` | Derecho comercial de ejecutar; no controla navegación ni genera candidaturas |

**Límites:** un `CandidateProfile` puede tener varias `Campaign`; una campaña admite múltiples `Application`; una candidatura se refiere a **una oportunidad canónica del candidato**, aunque aparezca en varios sitios. Las credenciales de los portales no forman parte del perfil; permanecen en el almacenamiento de sesiones del navegador cuando sea posible.

### 1.2. Entidades y value objects

```text
Account (id, identitySubject)
 ├─ 1..n CandidateProfile (id, version, sourceCvId, facts[])
 ├─ 0..n CvDocument (id, kind, originalId, currentVersion)
 ├─ 0..1 AccountSessionLease (instanceId, epoch, expiresAt)
 ├─ 0..n BrowserDevice (id, browserFamily, installationId)
 └─ 0..n Entitlement (status, validUntil)

CandidateProfile 1 ── 0..n Campaign (id, mandateVersion, status)
Campaign 1 ── 0..n Application (id, opportunityKey, result)
Application 1 ── 0..n SubmissionAttempt (id, phase, outcome, evidenceId)
Application 1 ── 0..n PendingItem (kind, actionRequired)
Campaign 1 ── 0..n AgentRun (deviceId, controllerTabId, epoch)
AgentRun 1 ── 0..n AgentStep (action, observationRef, outcome)
```

**Value objects:** `SearchConstraints` (sitios, máximo de postulaciones, especialización, ubicación, modalidad, salario/moneda/periodo, contrato, elegibilidad, exclusiones), `ProfessionalFact` (tipo, valor, procedencia y versión), `OpportunityIdentity` (sitio, identificador externo, URL normalizada, empresa/puesto), `ConsentScope` (sitios, acciones, Gmail, vigencia), `Evidence` (tipo, momento, referencia protegida), `Money` (importe/moneda) y `ExecutionLease` (campaña, dispositivo, pestaña, `epoch`, vencimiento).

**Invariantes de dominio:**

- Una contradicción con un filtro obligatorio impide emitir la orden de envío (`BR-03`, `BR-19`). La ausencia de dato crítico produce pendiente, no una suposición.
- Todo hecho biográfico utilizado en documento/mensaje debe referenciar un `ProfessionalFact` aportado por el candidato (`BR-07`).
- Una misma oportunidad canónica solo admite **un resultado confirmado** para un candidato; los reintentos no habilitan otro envío sin reconciliación (`BR-06`, `BR-10`).
- Los pasos irreversibles requieren permiso vigente, campaña activa y pestaña controladora abierta (`FR-40` y corrección posterior a la SRS).
- La confirmación se refiere a recepción por el destino, nunca a contratación o entrevista (`BR-11`).
- El CV original es inmutable; las variantes tienen identidad estable y versiones recuperables, sin expiración automática.
- El máximo de postulaciones pedido por el candidato se respeta reservando capacidad antes de cada envío; un resultado incierto mantiene su reserva hasta reconciliación.

### 1.3. Análisis de responsabilidades

`Campaign` decide si una acción **está permitida**; `Application` determina el **estado de postulación**; `AgentRun` coordina **cómo intentar** la acción; `BrowserAdapter` ejecuta **una orden validada**. Ningún proveedor LLM decide unilateralmente estas reglas. Esta separación permite revisar el agente sin modificar la política del producto.

## 2. Software Architecture Design

### 2.1. Estilo y distribución

**Monolito modular en la API + cliente web + extensión multiplataforma.** Un único backend Express concentra servicios y transacciones; no se fragmenta en microservicios. Next.js atiende la interfaz; el navegador del usuario contiene el ejecutor. Cloud Run no aloja campañas persistentes: atiende solicitudes individuales y devuelve órdenes para ejecutar localmente.

**Ubicación de los datos:**

- **Neon:** estado duradero, hechos corregidos, referencias y resúmenes de evidencia; acceso únicamente desde API.
- **Neon Object Storage:** CV y documentos generados en buckets privados; retención y eliminación por clase de archivo.
- **Extensión:** asociación de pestañas, checkpoint local mínimo, permisos y sesiones web existentes; almacenamiento local por instalación, cifrado de transporte al sincronizar.
- **Proveedor IA:** recibe únicamente el contexto necesario para un paso, enviado por backend; las claves de proveedor no salen del servidor.

**Identidad y sesiones:** Neon Auth administra usuarios y sesiones en PostgreSQL; Google OAuth es el único método de inicio de sesión. Next.js integra el SDK de Neon Auth y Express verifica los JWT mediante JWKS, incluidos emisor, audiencia y expiración. En producción se configuran credenciales OAuth propias y el callback de Neon. La extensión se vincula a la cuenta mediante un desafío de un solo uso originado desde la web. Iniciar sesión con Google no concede acceso a Gmail: la estrategia de operación mediante el navegador sigue siendo independiente. Una sola instancia de Mirai controla toda la cuenta, aunque se abra otra pestaña, navegador, ventana incógnita o equipo.

**Exclusividad de cuenta:** cada pestaña tiene un `instanceId` propio. Antes de acceder al control de Mirai, la API intenta adquirir un lease único por cuenta. Si existe otro vigente, la nueva instancia ofrece cancelar o transferir el control. La transferencia incrementa atómicamente un `accountEpoch`, invalida la instancia anterior y pausa la ejecución; reanudar requiere acción explícita. La API valida instancia y generación en operaciones de chat, campañas y comandos; serializa operaciones incompatibles del chat con Mirai y efectos externos, con idempotencia. La extensión comprueba el control vigente antes de cada acción y se detiene ante desconexión o vencimiento. Una acción externa ya iniciada no puede deshacerse: se reconcilia antes de repetirla. La expiración permite recuperar el control tras una caída.

### 2.2. Decisión clave: ciclo de vida de la pestaña controladora

**Contrato observable:** mientras la pestaña de la app que inició la campaña está abierta, puede trabajar el agente en pestañas secundarias sin robar el foco; **al cerrarla debe detener nuevos actos externos y pausar la campaña**. Al cerrar voluntariamente, se intentará mostrar la advertencia nativa de trabajo pendiente.

1. Al iniciar se registra `controllerTabId` + `deviceId` + `epoch`, con un **único ejecutor autorizado**.
2. Web y extensión establecen un canal de comunicación local; la extensión vigila `tabs.onRemoved`, desconexión del puerto y pérdida de la pestaña controladora, sin depender solo del servidor.
3. Al detectar cierre: el ejecutor activa inmediatamente su bandera local `paused`, revoca su permiso interno para nuevas acciones y persiste checkpoint. Se notifica a la API cuando haya red.
4. Antes de cada acción **y de toda acción irreversible**, se valida `controllerTabId`, control de cuenta vigente, permisos, versión del mandato y `epoch`. La pérdida de contacto o la expiración del lease implica **fail-closed**.
5. Reabrir la web presenta «Pausada», el último intento y un botón explícito **Reanudar**; no se reactiva automáticamente.

`beforeunload` solo permite un diálogo genérico si el navegador lo autoriza; **no** garantiza mostrar texto personalizado ni ejecutarse en todas las formas de cierre. Un clic externo que ya se ejecutó tampoco puede deshacerse: se reconcilia el resultado antes de continuar. **[T]** Heartbeat de controlador cada 3 s y lease de 10 s para detectar desconexiones silenciosas; medir falsa pausa en equipos reales. Verificación de cierre por evento local, sin esperar el TTL. [Referencias técnicas al final.]

### 2.3. Control de navegador multiplataforma

La extensión usa `tabs`, `scripting`/`content_scripts`, `storage` y mensajería WebExtensions, con permisos solicitados por sitio. Cada oportunidad usa una **pestaña propiedad del agente** (`active: false` donde sea posible); nunca reescribe ni enfoca la pestaña activa del usuario.

| Capacidad | Chromium (Chrome, Edge, Brave, Opera) | Firefox |
|---|---|---|
| Abrir/navegar pestañas secundarias | WebExtensions | WebExtensions |
| DOM accesible e interacción por scripts | Sí, según permisos | Sí, según permisos |
| Fondo de extensión | MV3 service worker | Construcción/ejecución adaptada a implementación Firefox |
| Captura visual de pestaña secundaria | Evaluar vía depuración/protocolo compatible | Evaluar capacidades equivalentes, distintas de Chromium |
| Interacción visual completa sin cambiar foco | **Requiere prueba específica** | **Requiere prueba específica** |

**Estrategia del ejecutor:** primero acciones DOM semánticas (`label`, roles, campos, clics y cambios); cuando sean insuficientes, usar observación visual **solo si el navegador admite capturar la pestaña gestionada sin mostrarla al usuario**. Si un flujo exige enfocar o capturar la pestaña que está usando el candidato, queda pendiente/limitado en ese navegador. La API de capturas visibles estándar no equivale a capturar cualquier pestaña en segundo plano.

WXT genera builds por navegador y permite diferencias puntuales en manifiestos/entrypoints; un paquete compartido define `BrowserPort`, y cada destino implementa `ChromiumAdapter` o `FirefoxAdapter`. No se promete paridad sin pruebas.

### 2.4. Motor del agente y autonomía

**Loop por tareas cortas:** `observar → interpretar → decidir → validar → actuar → verificar → registrar`. El backend es responsable de inferencia y decisión; la extensión ejecuta acciones permitidas y devuelve observaciones. Una tarea larga se compone de pasos explícitos; no depende de una única conexión HTTP abierta durante horas.

**Contratos internos:**

```ts
interface ModelPort {
  decide(input: AgentObservation): Promise<AgentDecision>;
  generateDocument(input: DocumentContext): Promise<GeneratedDocument>;
}
interface BrowserPort {
  observe(tabId: number): Promise<BrowserObservation>;
  execute(tabId: number, action: BrowserAction): Promise<ActionReceipt>;
  isControllerAlive(controllerTabId: number): Promise<boolean>;
}
type AgentDecision =
  | { kind: 'act'; action: BrowserAction }
  | { kind: 'pending'; reason: string }
  | { kind: 'complete'; result: 'confirmed' | 'unconfirmed' | 'failed' };
```

**Evaluación de modelos:** Gemini 4 Carbon participa como candidato junto a otros modelos disponibles. Se comparan **éxitos confirmados, errores por restricciones, pasos, latencia y costo por postulación** en los mismos escenarios. El `ModelPort` traduce las acciones de cada proveedor al esquema propio; si el proveedor solicita confirmación obligatoria, la ejecución la respeta o genera pendiente.

### 2.5. Consecuencias de calidad

- Escalado independiente de frontend/API mediante Cloud Run; costo de navegador aportado por dispositivo del candidato.
- La API puede caer y recuperarse sin perder candidaturas porque cada transición crítica se persiste en Neon; el navegador se detiene cuando no puede autorizar una acción.
- El servidor impone límites técnicos de concurrencia y gasto por seguridad operativa, **no** cuotas arbitrarias de oportunidades elegibles. La exclusividad se aplica a toda la cuenta.
- La extensión debe sobrevivir a la suspensión/recreación de su *background* mediante almacenamiento persistente y registro de eventos; jamás asumir proceso en memoria permanente.

## 4. Behavioral Modeling — UML State Machines

Los siguientes autómatas son **independientes**: estado de campaña ≠ estado de conexión ≠ resultado de candidatura.

### 4.1. Campaña

```text
DRAFT ── perfil/permiso/pago válidos ──> READY
READY ── usuario inicia + pestaña vinculada ──> ACTIVE
ACTIVE ── pausa / cierre pestaña / revocación / fallo crítico ──> PAUSED
PAUSED ── usuario reanuda + validaciones vigentes ──> ACTIVE
READY | ACTIVE | PAUSED ── usuario termina ──> FINISHED
```

**Reglas:** `FINISHED` es terminal. Pausar no cancela solicitudes ya recibidas por terceros. Cambiar restricciones incrementa `mandate_version` y reevalúa únicamente trabajo futuro. Un intento en progreso puede quedar `unconfirmed` tras la pausa.

### 4.2. Ejecutoria local (`AgentRun`)

```text
CREATED -> LEASED -> OBSERVING -> DECIDING -> EXECUTING -> VERIFYING
                |       |           |           |          |
                +-------+-----------+-----------+----------+--> CHECKPOINTED
CHECKPOINTED -> LEASED (siguiente acción autorizada)
[desde cualquier estado] -> STOPPED (cierre/pausa/revocación)
[sin red, estado desconocido] -> RECOVERY_REQUIRED
RECOVERY_REQUIRED -> RECONCILING -> LEASED | STOPPED | REVIEW_REQUIRED
```

**Control de cuenta y campaña:** el lease de cuenta usa `account_id`, `instance_id` y `account_epoch` monotónico; cada lease de campaña pertenece a esa instancia y generación. La transferencia invalida los leases de ejecución anteriores. Un comando con generación obsoleta se rechaza; el lease no convierte un envío externo en transacción de base de datos.

### 4.3. Candidatura y envío

| Estado | Transiciones válidas | Condición |
|---|---|---|
| `discovered` | `excluded`, `eligible`, `pending_review` | filtros/identidad evaluados |
| `eligible` | `preparing`, `excluded` | vigente y no duplicada |
| `preparing` | `ready_to_submit`, `pending_review`, `failed` | documentos/campos suficientes |
| `ready_to_submit` | `submitting`, `pending_review` | comprobación final de permiso y lease |
| `submitting` | `confirmed`, `unconfirmed`, `failed` | señal observable del destino |
| `unconfirmed` | `confirmed`, `pending_review`, `failed` | reconciliación, nunca reenvío ciego |
| `pending_review` | estado anterior apropiado o `excluded` | usuario resuelve o desiste |
| `confirmed` / `excluded` / `failed` | terminal para ese intento | seguimiento se modela aparte |

**Transición atómica local:** `eligible → preparing` solo la reclama un ejecutor; `ready_to_submit → submitting` crea antes un `SubmissionAttempt` con `intent_key` único. Al reaparecer el trabajo, se consulta el destino si hay posibilidad de envío previo. Si permanece ambiguo, se conserva `unconfirmed`.

### 4.4. Pendientes y comunicaciones

- `PendingItem`: `open → resolved | dismissed`; `resolved` vuelve elegible **solo** al trabajo afectado; un pendiente de autenticación no otorga por sí mismo permiso para otra cuenta.
- Cada envío externo usa una intención idempotente y, cuando esté disponible, una referencia opaca del canal para evitar duplicados; el hilo permanece en el portal o correo, sin historial paralelo en Mirai.
- `Offer/Interview`: evento recibido y notificado; **no cambia** retroactivamente el resultado de postulación.

## 5. Interaction & Workflow Modeling — Sequence / Activity

### 5.1. Inicio y vinculación

```text
Usuario -> Web: CV + instrucción natural + consentimiento
Web -> API: adquirir control de cuenta; crear perfil y mandato verificable
API -> Neon PostgreSQL / Object Storage: guardar metadatos / CV
Web -> Extensión: solicitud de vinculación + desafío efímero
Extensión -> API: comprobar desafío y asociar deviceId
Usuario -> Web: Iniciar
Web -> API: start(campaignId, controllerTabId, deviceId)
API -> Neon: verificar entitlement + concesión epoch/lease
API -> Web/Extensión: autorizado, estado ACTIVE
```

El intérprete transforma la instrucción natural en fuentes, restricciones, especialización y máximo solicitados; pide solo datos indispensables que falten o sean ambiguos. La extracción de CV produce hechos revisables. Al concluir, Mirai notifica y entrega un reporte con postulaciones, descartes, pendientes y resultados.

### 5.2. Ciclo de postulación

```text
Extensión -> API: nextStep(campaign, epoch, observación)
API -> Domain: validar control de cuenta, vigencia, fuentes, filtros, límite y deduplicación
API -> ModelPort: elegir siguiente acción / redactar con hechos trazables
ModelPort -> API: acción tipada o pendiente
API -> Extensión: acción autorizada + stepId + mandateVersion
Extensión -> BrowserAdapter: validar pestaña/epoch; interactuar
Extensión -> API: receipt(stepId, observación, resultado)
API -> Neon PostgreSQL / Object Storage: checkpoint + evidencia saneada
[si acción final fue enviar]
  API: reconciliar señal observable; confirmed | unconfirmed | failed
[si requiere dato personal]
  API: pending_review y avanzar con la siguiente oportunidad
```

**Envío externo:** antes de pulsar «Enviar», la API reserva atómicamente el intento y una plaza del máximo indicado; los intentos confirmados y aquellos cuyo resultado es incierto ocupan plaza hasta su reconciliación. La extensión comprueba nuevamente el estado local. Un `HTTP 200` de la API nunca se interpreta como confirmación del ATS.

### 5.3. Cierre, interrupción y vuelta

```text
Usuario -> Navegador: cerrar pestaña de la web app
Web: intentar aviso genérico de trabajo pendiente
Navegador -> Extensión: tab removed / port disconnected
Extensión: STOPPED + checkpoint; bloquear siguientes acciones
Extensión -> API: pause(reason=controller_closed), cuando sea posible
API -> Neon: PAUSED; revocar lease

[usuario abre web después]
Web -> API: leer campaña e intentos inciertos
Usuario -> Web: Reanudar
API -> Extensión: nuevo epoch
Extensión -> Portal: reconciliar posible envío previo
Extensión -> API: resultado; retomar trabajo no enviado
```

Si Chrome se cierra por completo, no existe ejecutor local. El vencimiento del lease evita que un cliente rezagado siga solicitando nuevas acciones cuando vuelva la conectividad.

### 5.4. Seguimiento por Gmail

```text
Extensión -> Gmail UI: consultar correo relacionado con campaña
Extensión -> API: resumen/contexto de mensaje relevante
API -> Domain: verificar contexto, autorización vigente y datos disponibles
API -> ModelPort: redactar respuesta basada en perfil
API -> Extensión: instrucción tipada y controlada
Extensión -> Gmail UI: enviar por cuenta autorizada
Extensión -> API: observar resultado y guardar estado mínimo para evitar duplicados
```

En el MVP, Gmail se usa a través del navegador. El agente se comunica únicamente en plataformas laborales o por correo autorizado; una autorización previa cubre comunicaciones posteriores dentro de su alcance hasta revocación. No se procesa el buzón completo ni se crea una bandeja o historial de conversaciones en Mirai; se deriva al candidato lo que requiera su intervención.

## 6. Data Modeling & Database Design

### 6.1. Esquema lógico/físico (PostgreSQL)

| Tabla | Campos principales | Claves e índices |
|---|---|---|
| `accounts` | `id uuid`, `identity_sub text`, `created_at timestamptz` | PK; `unique(identity_sub)` |
| `profiles` | `id`, `account_id`, `version int`, `facts jsonb`, `source_cv_file_id`, `updated_at` | FK account; `unique(account_id, version)` |
| `files` | `id`, `account_id`, `object_key`, `mime`, `size_bytes`, `retention_class`, `expires_at nullable` | FK account; índice `expires_at` para temporales |

**Tipos:** UUID generados en API/DB; `timestamptz` en UTC; estados como enums validados por dominio y restricciones `CHECK`; `jsonb` reservado a hechos y parámetros de estructura variable, no para reemplazar las relaciones principales.

**Normalización de duplicados:** `canonical_key` se calcula primero con `(sitio, external_ref)` si existe; si una oferta se republica en otro sitio, se buscan coincidencias adicionales por `(empresa normalizada, rol, ubicación, URL destino ATS)` y se conserva alias de fuente en `opportunity_sources` si se necesita. **Una coincidencia probable no autoriza automáticamente eliminar una oportunidad distinta**: duda → revisión de identidad.

**Control de concurrencia:** adquirir o transferir el lease de cuenta mediante transacción y CAS; verificar generación en cada operación. Serializar operaciones incompatibles del chat con Mirai y los envíos externos; reservar plazas del máximo en la misma transacción que el intento. Usar `UPDATE ... WHERE epoch = ? AND state = ...`, comprobar filas afectadas y exigir unicidad de `intent_key` para impedir envíos duplicados. Se admiten transacciones interactivas mediante un controlador de conexión compatible cuando la operación las requiera; las consultas simples pueden usar el driver HTTP de Neon.

### 6.2. Datos locales y archivos

- `browser.storage.local` / IndexedDB en la extensión: `installationId`, pestañas propias, último checkpoint y colas de **recibos pendientes de sincronizar**, sin copiar cookies ni contraseñas de portales.
- Neon Object Storage: bucket privado y claves opacas `accounts/{accountId}/...`; acceso de servicio, sin enlaces públicos permanentes. Subida/descarga mediante URLs firmadas de corta vida emitidas por Express tras comprobar titularidad.
- CV originales y variantes: archivos permanentes sin `expires_at`; cada variante conserva identidad estable y versiones internas recuperables, con comparación de cambios. El usuario puede ver, descargar, renombrar y borrar documentos o pedir al agente que edite una variante. Para editar el original se crea una copia. Documentos temporales de una candidatura son una clase distinta: una tarea programada elimina solo esos objetos vencidos y actualiza referencias, con reintentos. La eliminación solicitada de cuenta incluye los archivos.
- Eventos de PostHog: IDs técnicos seudónimos, estado, navegador, portal y métricas agregadas; **excluir CV, prompts completos, correos, capturas y datos de reclutadores**. Autocaptura/replay deshabilitados en vistas sensibles.

### 6.3. Conservación e inactividad

| Clase | Estrategia |
|---|---|
| Sesión del navegador/credenciales del portal | En el perfil local del navegador, bajo control de su titular; no exportarlas al servidor |
| CV original, variantes e historial de versiones | Sin TTL ni expiración automática; conservar hasta solicitud de borrado del usuario |
| Capturas y documentos temporales de postulación | Retención configurable y limpieza automática una vez superada la utilidad operativa |
| Candidaturas y evidencias mínimas de envío | Resumen persistente mientras sea necesario para seguimiento/soporte; purga con política publicada |
| Cuenta sin actividad prolongada | La inactividad no elimina automáticamente los CV ni sus variantes |

Los períodos de retención de las clases temporales se mantienen **configurables por clase y región**, sujetos a política publicada y obligaciones de conservación; evitar hardcodearlos en el esquema. Un objeto borrado no debe quedar recuperable mediante URL firmada antigua.

## 7. API & Interface Contract Design

### 7.1. Reglas de protocolo

- Prefijo REST `/v1`; JSON UTF-8; validación Zod en entrada/salida; documentación OpenAPI generada desde contratos versionados.
- Token de identidad verificable y autorización por propietario en cada endpoint protegido; control de instancia vigente en las operaciones de Mirai. La adquisición y transferencia de control admiten la instancia autenticada aún no activa. Extensión vinculada aporta `deviceId` y desafío/capacidad de sesión de duración limitada; nunca un token de proveedor IA.
- `Idempotency-Key` requerido en inicios, comandos sensibles, confirmación de acciones y resoluciones; `409 CONFLICT` ante lease/versión incompatible.
- `accountEpoch`, `mandateVersion` y `epoch` obligatorios en órdenes de agente; la API vuelve a comprobar filtros/consentimiento antes de ordenar efectos externos.
- Canal app↔extensión: `runtime.connect/sendMessage` donde esté soportado; `externally_connectable` con origen exacto en Chromium y puente `content_script` controlado en Firefox cuando corresponda. Mensajes autenticados por desafío de emparejamiento, `origin`, `tabId` y versión.

### 7.2. Endpoints principales

| Método y ruta | Solicitud → respuesta | Restricción |
|---|---|---|
| `POST /v1/session/acquire` | instancia → control o conflicto | exclusividad por cuenta |
| `POST /v1/session/transfer` | instancia → nueva generación | invalida control anterior y pausa ejecución |
| `POST /v1/session/heartbeat` | instancia + generación → renovación | solo titular vigente |
| `POST /v1/profiles/cv` | metadatos de archivo → URL firmada + fileId | propietario y límite de tamaño |
| `GET /v1/cv-documents` | biblioteca y versiones | propietario |
| `POST /v1/cv-documents/:id/copy` | original o variante → nueva variante | original inmutable |
| `GET /v1/cv-documents/:id/versions` | historial y diferencias | propietario |
| `PATCH /v1/cv-documents/:id` | renombrar o editar variante → versión | control de versión; nunca sobrescribir original |
| `GET /v1/cv-documents/:id/download` | URL firmada de corta vida | propietario |
| `DELETE /v1/cv-documents/:id` | borrar documento y versiones | propietario; mantener integridad de referencias |
| `POST /v1/instructions` | mensaje natural → mandato estructurado o aclaración | control vigente; sin inferir datos críticos |
| `POST /v1/profiles/extract` | `{fileId}` → hechos propuestos y procedencia | salida no confirmada por usuario |
| `PUT /v1/profiles/:id` | hechos validados/versionados → nueva versión | control `If-Match` |
| `POST /v1/campaigns` | perfil + filtros + preferencias → campaña `draft`/`ready` | pertenencia y esquema |
| `POST /v1/devices/link-challenge` | navegador → desafío de un solo uso | sesión web autorizada |
| `POST /v1/devices/link` | desafío + instalación → vínculo | TTL, un solo canje |
| `POST /v1/campaigns/:id/start` | dispositivo + pestaña → lease/epoch | permiso, pago, controladora abierta |
| `POST /v1/campaigns/:id/pause` | motivo + epoch → `paused` | revoca capacidad de ejecución |
| `POST /v1/campaigns/:id/resume` | dispositivo + nueva pestaña → epoch nuevo | intervención explícita |
| `GET /v1/campaigns/:id` | estado + resumen | solo titular |
| `GET /v1/applications?campaignId=…` | resultados paginados | solo titular |
| `GET /v1/applications/:id` | oportunidad, estado, intentos, evidencia | URL de evidencia temporal |
| `GET /v1/pending?campaignId=…` | pendientes paginados | solo titular |
| `POST /v1/pending/:id/resolve` | dato/resolución → estado revisado | no dispara reenvío ciego |
| `POST /v1/agent/next` | observación + epoch + stepId → acción tipada | ejecutor vinculado, activo |
| `POST /v1/agent/receipt` | recibo de acción + observación → checkpoint | idempotencia de `stepId` |
| `GET /v1/activity?campaignId=…` | eventos y costos agregados | no expone contenido sensible |
| `POST /v1/privacy/delete-request` | solicitud → estado del trámite | autorización reforzada |

**Campañas y correo:** los envíos a Gmail suceden en la extensión dentro del canal autorizado. Mirai no expone endpoints de bandeja ni historial de conversaciones externas; conserva únicamente el estado operativo para evitar duplicados y la actividad pertinente al dashboard.

### 7.3. Esquema de comando y recibo

```ts
type BrowserCommand = {
  commandId: string;
  campaignId: string;
  epoch: number;
  accountEpoch: number;
  mandateVersion: number;
  controllerTabId: number;
  targetTabId: number;
  expiresAt: string;
  action:
    | { type: 'navigate'; url: string }
    | { type: 'click'; locator: { role?: string; name?: string; selector?: string } }
    | { type: 'type'; locator: { selector?: string }; valueRef: string }
    | { type: 'upload'; locator: { selector?: string }; fileId: string }
    | { type: 'observe'; format: 'dom' | 'screenshot' }
    | { type: 'submit'; submissionIntentKey: string };
};
type ActionReceipt = {
  commandId: string;
  epoch: number;
  status: 'executed' | 'blocked' | 'failed' | 'uncertain';
  observedUrl?: string;
  evidenceRef?: string;
  observedAt: string;
};
```

El `valueRef` referencia contenido autorizado del perfil/documento para ese paso; **no** se registra el texto del campo en telemetría. Los comandos caducados, de otra pestaña o de un dominio sin permiso se rechazan en la extensión.

### 7.4. Errores y compatibilidad

```json
{
  "error": {
    "code": "MANDATE_VERSION_MISMATCH",
    "message": "La configuración cambió; actualiza el estado antes de continuar.",
    "requestId": "req_...",
    "retryable": false
  }
}
```

Códigos canónicos: `AUTH_REQUIRED` (401), `FORBIDDEN_SCOPE` (403), `NOT_FOUND` (404), `CONFLICTING_EXECUTOR` (409), `MANDATE_VERSION_MISMATCH` (409), `CONTROLLER_CLOSED` (409), `PENDING_INPUT` (422), `RATE_LIMITED` (429), `MODEL_UNAVAILABLE` (503) y `EXTERNAL_OUTCOME_UNKNOWN` (409/estado de intento). Cambios compatibles agregan campos opcionales; cambios incompatibles exigen nueva versión de contrato y coordinación con versiones de extensión instaladas.

## 8. Security Architecture & Threat Modeling

### 8.1. Activos y fronteras de confianza

**Activos:** CV, trayectoria, contacto, conversaciones de reclutadores, documentos generados, autorización de postular, sesiones externas, tokens de identidad, facturación y registros de envío.

**Fronteras:** (1) web app ↔ extensión; (2) dispositivo ↔ API; (3) API ↔ Neon y Vertex AI; (4) agente ↔ sitios y mensajes externos. DOM, ofertas, correos, resultados del LLM y payloads enviados por clientes son **entradas no confiables**.

### 8.2. Amenazas y controles

| Amenaza | Control arquitectónico | Prueba de aceptación |
|---|---|---|
| Prompt injection en oferta o email | Instrucciones del usuario separadas de texto externo; acciones permitidas como lista cerrada y validadas por `CampaignPolicy` | Oferta maliciosa no cambia filtros ni envía CV a dominio ajeno |
| Exfiltración de CV a un sitio inesperado | `allowlist` dinámica basada en consentimiento + dominio destino verificable + subida limitada a formulario elegido | Upload a host no autorizado bloqueado |
| Token/clave IA filtrado en extensión | Claves exclusivamente en servicio API; Secret Manager; credenciales cortas para vínculo local | Build no contiene secretos de proveedor |
| Dos instancias de la misma cuenta actúan a la vez | Lease de cuenta, `accountEpoch`, CAS y serialización de operaciones incompatibles; invalidar leases de campaña al transferir | Segunda instancia cancela o transfiere; órdenes atrasadas se rechazan y operaciones en curso se reconcilian |
| Cierre de pestaña mientras ejecuta | `onRemoved`/desconexión + bandera de parada + verificación antes de cada acto irreversible | No comienza otro envío tras detectar cierre |
| Reenvío después de respuesta perdida | `SubmissionAttempt` previo + `unconfirmed` + reconciliación por UI del destino | No hay segundo clic automático ante resultado ambiguo |
| Lectura de datos entre cuentas (IDOR) | Identidad verificada + filtro owner en consultas y acceso a objetos de Neon | Cuenta A no lee CV, solicitudes ni correos de B |
| Suplantación del puente web-extensión | `origin` estricto, pestaña vinculada, desafío efímero, mensajes tipados, expiración | Pestaña de otro dominio no da órdenes |
| Acceso excesivo a Gmail | Solo cuenta/hilos laborales autorizados; no borrar ni modificar correos irrelevantes | Mensaje personal no es procesado ni contestado |
| Captura accidental de PII | Telemetría saneada, snapshots efímeros, evidencias privadas con expiración | CV/correo no aparece en eventos PostHog |
| Pérdida de consentimiento | Comprobar vigencia + mandato por operación; revocar lease al cambiar permisos | Comando antiguo rechazado |
| Costo descontrolado del agente | Tope técnico de pasos/tokens por ejecución; pausa explicada ante anomalía; métricas por resultado | Ciclo recursivo no consume recursos ilimitados |

**Permisos mínimos de extensión:** solicitar acceso por sitio durante vinculación o primera navegación. No usar permisos universales permanentes si el navegador permite host permissions opcionales. Evitar interceptar teclado/mouse del sistema. El candidato controla la cuenta externa y cualquier reautenticación que exija su presencia.

**Modelo de responsabilidad:** la extensión nunca ejecuta instrucciones textuales arbitrarias del modelo; solo comandos tipados. Los datos del CV se tratan como declaraciones del usuario, sin que la IA les añada experiencia o credenciales.

### 8.3. Verificación de controles

Vitest cubre políticas, permisos, redacción basada en hechos, parseo Zod, estados, CAS y deduplicación mediante adaptadores falsos; pruebas de navegador real y escenarios E2E se ejecutarán en la fase de verificación con evidencias reproducibles. Los logs operativos son estructurados, con identificador de solicitud, campaña y tipo de fallo, sin payloads sensibles.

## 9. Architecture Decision Records — ADR

Las entradas siguientes resumen **decisión, alternativa significativa y consecuencia específica**, evitando volver a argumentar todo el diseño.

| ADR | Decisión | Alternativa descartada / consecuencia |
|---|---|---|
| **ADR-001** | Web app + extensión local WXT | Navegadores cloud por sesión: mayor gasto y operación; depende de equipo del usuario |
| **ADR-002** | Node/Express modular, sin microservicios iniciales | Servicios independientes: coordinación innecesaria para MVP; módulos mantienen fronteras |
| **ADR-003** | Neon PostgreSQL + Drizzle | Base de datos con cómputo siempre encendido; requiere gestionar cold start y acceso externo |
| **ADR-004** | Servicios web/API en Cloud Run + archivos privados en Neon Object Storage | VM permanente; scale-to-zero y retención gestionada por la aplicación |
| **ADR-005** | Inferencia solo mediante `ModelPort` en API | Acoplar la extensión a un LLM; permite comparación de Carbon y alternativas |
| **ADR-006** | `ControllerWatch` como autoridad local de pausa | Continuar al cerrar web; obliga a lease/checkpoints y reanudación explícita |
| **ADR-007** | Una instancia por cuenta y `epoch` monotónico | Pestañas/dispositivos competidores; evita doble coordinación |
| **ADR-008** | Envíos con `SubmissionAttempt` y estado incierto | Reintento automático indiscriminado; requiere reconciliación externa |
| **ADR-009** | Gmail mediante UI del navegador en MVP | Integración Gmail API simultánea; evita dos ejecutores y nuevos permisos OAuth |
| **ADR-010** | Compatibilidad Chromium + Firefox mediante adaptadores | Código solo para `chrome.debugger`; ciertas acciones visuales requieren fallbacks |
| **ADR-011** | Autorización tipada, DOM-first y visión condicional | Clics visuales sin validación; reduce riesgo de interrumpir al usuario |
| **ADR-012** | Vitest + PostHog inicialmente | Múltiples suites y observabilidad duplicada; ampliar cobertura cuando lo exija evidencia |
| **ADR-013** | Identidad gestionada por Neon Auth con Google OAuth | Autenticación desarrollada desde cero; verificar tokens por API |

**Puntos que se resuelven con pruebas de capacidad, sin cambiar el contrato de producto:** captura visual en segundo plano por navegador; versión exacta de manifiesto en cada store; controladores compatibles de transacciones Drizzle/Neon; candidato LLM seleccionado; límites de pasos/costo y tamaños máximos de archivo.

## 10. Dirección de experiencia

La interacción principal es conversacional, similar a un chat de IA, acompañada de un panel de actividad y control del agente con una tabla tipo hoja de cálculo. Sus posibles datos incluyen fecha de postulación, empresa, CV usado y mensajes directos; las columnas y el diseño no están definidos. No hay bandeja propia de comunicaciones. La dirección visual es oscura, con Vercel como referencia. La gestión de CV permite consultar documentos y diferencias entre versiones; los estados y acciones deben ser accesibles por teclado y no depender solo del color.
