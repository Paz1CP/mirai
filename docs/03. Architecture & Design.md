## 1. Purpose & Architectural Drivers

Este documento define la estructura técnica de Mirai, las fronteras entre componentes, los modelos de dominio, los contratos de comunicación, las decisiones arquitectónicas y las propiedades de calidad que deben guiar el desarrollo.

La arquitectura debe resolver cinco problemas centrales:

1. **Autonomía sobre interfaces externas:** el agente necesita operar sitios laborales reales, con formularios y estados heterogéneos.
2. **Control del usuario:** el navegador, las sesiones, los permisos y las acciones personales permanecen bajo autoridad del candidato.
3. **Ejecución recuperable:** las interrupciones no pueden provocar pérdida de resultados ni envíos duplicados.
4. **Trazabilidad:** cada candidatura conserva campaña, datos de la oportunidad, resultado y referencias documentales actuales.
5. **Costo controlado:** inferencia, almacenamiento, pagos y operaciones deben producir métricas atribuibles.

### 1.1. Principios

- Modular monolith para el backend de dominio; no distribuir servicios sin una necesidad demostrable.
- Separar UI, API, extensión, runtime del agente y contratos compartidos.
- Mantener los secretos de proveedores en el servidor.
- Validar entradas y salidas mediante contratos tipados.
- Tratar portales, páginas, correos y documentos externos como datos no confiables.
- Persistir los efectos externos antes de permitir reintentos.
- Mantener la semántica de negocio independiente del proveedor LLM.
- Priorizar Chrome/Chromium de escritorio para la ejecución del navegador.
- No presentar como universal una capacidad que depende de una fuente externa.

## 2. System Context — C4 Level 1

### 2.1. Sistema y actores

| Elemento | Responsabilidad |
|---|---|
| Candidato | Define el mandato, aporta perfil, controla permisos y revisa resultados |
| Mirai Web | Interfaz de acceso, chat, perfil, biblioteca, dashboard y control |
| Mirai API | Identidad, dominio, persistencia, coordinación, billing y comunicación |
| Mirai Extension | Vincula el navegador local y ejecuta operaciones de control autorizadas |
| Job Portals / ATS | Fuentes de oportunidades y destinos de candidaturas |
| Gmail / portales de mensajería | Canales externos de comunicación cuando el usuario los autoriza |
| Google ADK / Vertex AI | Runtime de agente, sesiones e inferencia |
| Neon | Identidad, PostgreSQL y almacenamiento de documentos |
| Paddle | Procesamiento de pagos y eventos comerciales |

### 2.2. Frontera de confianza

Mirai controla sus interfaces, su backend, su base de datos y su extensión. No controla el HTML, los formularios, los mensajes, las sesiones, los desafíos ni las políticas de los sitios externos.

Una página externa nunca puede modificar el mandato, conceder permisos, cambiar el límite de candidaturas ni solicitar datos de otra cuenta. El agente recibe el contenido externo como contexto no confiable y utiliza herramientas delimitadas por el scope de ejecución.

## 4. Backend Architecture

### 4.1. Composition Root

El punto de composición se concentra en **apps/api/src/bootstrap/app.ts**. El servidor HTTP se inicia desde **apps/api/src/bootstrap/server.ts** y adjunta el handler del workspace WebSocket al mismo servidor.

El bootstrap conecta:

- Verificador de identidad.
- Base de datos y repositorios.
- Perfil, extracción y almacenamiento.
- Biblioteca de CV.
- Repositorio de candidaturas y campañas.
- Sesiones de chat y runtime del agente.
- Workspace del navegador.
- Wallet, billing de inferencia y Paddle.

Las features reciben dependencias explícitas. Los repositorios no deben crear clientes globales de infraestructura ni importar componentes de UI.

### 4.2. Domain Modules

| Módulo | Responsabilidad | Frontera |
|---|---|---|
| Auth | Identidad, sesión activa, permisos de cuenta y eliminación | Neon Auth y tokens |
| Profiles | Datos profesionales, preferencias, extracción y documentos fuente | Perfil del candidato |
| CVs | Originales, CV principal, variantes y selección documental | Biblioteca profesional |
| Agents | Interpretación, herramientas, turnos, streaming y ejecución | Coordinación inteligente |
| Sessions | Conexión de workspace, ownership y control de navegador | Ciclo de vida de conexión |
| Campaigns | Mandato, criterios, límite y ciclo de vida | Trabajo de búsqueda |
| Applications | Resultado, referencias documentales, consulta y dashboard | Registro de candidaturas |
| Billing | Wallet, movimientos, consumo y pagos | Entitlements y economía |

Dashboard es una vista de consulta del dominio Applications; no constituye un dominio de escritura separado. La biblioteca de documentos se expresa mediante CVs; no requiere una feature genérica Documents.

### 4.3. Dependency Direction

- Web depende de contratos y APIs; no accede directamente a PostgreSQL ni a secretos de proveedores.
- Extension depende de contratos compartidos y APIs de navegador; no contiene reglas de negocio.
- API depende de contratos, repositorios e infraestructura.
- Agent depende de interfaces de dominio para perfil, CV, campañas, candidaturas y billing.
- Los módulos de dominio no dependen de componentes React ni de APIs de Chrome.
- Los contratos compartidos no importan implementación de API, web o extensión.

## 5. Agent Runtime Architecture

### 5.1. Componentes

| Componente | Responsabilidad |
|---|---|
| Managed Chats | Ciclo de vida, propiedad y lectura de sesiones conversacionales |
| Mirai Agent | Definición del agente, modelo, instrucciones y herramientas |
| Mirai Tools | Operaciones de dominio expuestas al agente |
| Playwright Tools | Descubrimiento y exposición de herramientas de navegador mediante MCP |
| Chat Execution | Turnos, cola, pausas, reanudación, eventos y recuperación |
| Streaming Gemini | Adaptación del streaming y continuidad de interacciones |
| Context Compactor | Reducción de contexto preservando mandato y datos relevantes |
| Chat Events | Normalización de eventos y resultados visibles |

### 5.2. Runtime y modelo

El runtime utiliza Google ADK y sesiones administradas mediante Vertex AI Agent Engine. La inferencia se configura del lado del servidor con Google GenAI y modelos Gemini.

El modelo se selecciona mediante configuración de entorno. El agente no debe depender de un nombre de modelo fijo en reglas de dominio. Las operaciones de inferencia se identifican por tipo:

- chat
- compaction
- cv_extraction

La selección de modelo, región, límites y tarifas se centraliza en configuración y billing.

### 5.3. Domain Tools

El agente recibe herramientas de negocio delimitadas por una estructura de ejecución que identifica cuenta, chat, comando, campaña y límites de la tarea.

Herramientas principales:

| Tool | Uso |
|---|---|
| getCandidateContext | Leer perfil, preferencias y permisos vigentes |
| listDocuments | Consultar biblioteca de documentos |
| getDocument | Leer el contenido o referencia de un documento autorizado |
| createCampaign | Crear un mandato persistente |
| listCampaigns | Consultar campañas |
| selectCampaign | Seleccionar una campaña y, si el usuario lo pide, reanudarla |
| updateCampaign | Modificar mandato, criterios, límite o estado |
| recordApplication | Registrar un resultado de candidatura |
| listApplications | Consultar resultados para evitar repetición |
| getApplication | Consultar un registro específico antes de actualizar o reintentar |

Las herramientas validan sus argumentos y el ownership de cada recurso. Una herramienta no concede permisos por el hecho de ser invocada por el modelo.

### 5.4. Execution Flow

1. El candidato envía una instrucción desde el chat.
2. La API valida identidad, sesión, ownership y estado de ejecución.
3. Chat Execution recupera o crea la sesión administrada.
4. Mirai Agent recibe el mensaje, el contexto permitido y las herramientas aplicables.
5. El agente consulta perfil, preferencias, documentos y campañas mediante herramientas de dominio.
6. Cuando necesita navegar, solicita herramientas Playwright mediante MCP.
7. El workspace resuelve la conexión con la extensión y el navegador local.
8. Los eventos y resultados regresan al runtime.
9. El agente registra campañas y candidaturas mediante las herramientas de dominio.
10. La API publica eventos normalizados para la interfaz y concilia consumo de inferencia.

La salida del modelo nunca sustituye la validación de reglas, permisos, ownership ni persistencia.

## 6. Browser Workspace Architecture

### 6.1. Operating Model

El navegador pertenece al candidato y se ejecuta en su equipo. La extensión conecta el navegador local con la aplicación y el backend. Mirai no depende de un navegador remoto alojado como entorno primario de ejecución.

La ruta principal de control es:

**Agent → Playwright MCP → BrowserModel → Workspace WebSocket → Extension Workspace → Chrome Debugger API / CDP → Chrome local**. Los resultados y eventos recorren el camino inverso.

### 6.2. Components

- **Workspace WebSocket:** endpoint compartido por web y extensión en **/v1/workspace**.
- **Extension Background:** valida origen, pestaña, frame y disponibilidad de la API de depuración.
- **Workspace Client:** mantiene la conexión, heartbeat, comandos, respuestas y transferencia de control.
- **Remote Browser Bridge:** traduce comandos de extensión y Chrome Debugger.
- **BrowserModel:** adapta tabs, targets, sesiones CDP y eventos al modelo de navegador consumido por Playwright.
- **Playwright MCP:** expone navegación, snapshots, capturas, interacción, formularios, pestañas, espera, archivos y diálogos como herramientas del agente.

### 6.3. Browser Control Rules

- Una cuenta mantiene un instance_id en users.account_controllers. El backend coordina ownership mediante advisory locks.
- La ruta de extensión permite adjuntar otro puerto autorizado de Mirai al workspace existente; la ruta web de compatibilidad sustituye el controlador y espera la liberación de su lock.
- La pestaña controladora queda protegida; el inventario expone las demás pestañas del perfil, sin clasificación personal/de trabajo.
- Las navegaciones admiten HTTP/HTTPS sin credenciales embebidas; about:blank es el estado inicial. Las pestañas nuevas se abren inactivas.
- La extensión restringe comandos CDP, incluido DOM.setFileInputFiles. La preparación de adjuntos en backend no completa su carga en el portal.
- Stop cancela el turno; la pérdida del WebSocket cancela sus ejecuciones. Cerrar solo la página Mirai no equivale a Stop en la ruta de extensión.
- La renovación controlada conserva checkpoints; una desconexión ordinaria requiere reanudación explícita de campañas detenidas.
- Los comandos y respuestas se validan mediante contratos y límites de tamaño.

Detalle: [Browser — Técnico](browser/technical.md).

### 6.4. Browser Compatibility

La dependencia de Chrome Debugger API define Chrome de escritorio y navegadores Chromium compatibles como objetivo principal de ejecución. La compilación de una extensión para Firefox no equivale por sí sola a compatibilidad del control CDP. Firefox requiere una capa de adaptación que satisfaga el mismo contrato de Browser Workspace.

El MVP no ejecuta campañas desde dispositivos móviles.

## 7. Domain & Data Model

### 7.1. Identity

La identidad se delega a Neon Auth. El backend valida JWT mediante JWKS, issuer, audience, expiración, rol y sesión activa. La identidad externa se representa internamente mediante accountId.

### 7.2. Core Entities

| Entidad | Atributos conceptuales | Relación |
|---|---|---|
| Account | id, status, createdAt | Propietaria de los recursos |
| CandidateProfile | profile, extraction, confirmed, revision | Una por cuenta |
| JobPreferences | roles, seniority, industry, mode, location, salary, schedule, contract, language, mobility, rules | Una por cuenta |
| OriginalDocument | id, name, storageKey, createdAt | Archivo fuente separado, eliminable por el candidato |
| CvDocument | id, kind, name, specialization, profile, sourceKey, isDefault, revision | Registro del principal o de una variante editable |
| ChatSession | id, accountId, title, updatedAt | Sesión administrada por el runtime |
| ChatAttachment | id, accountId, chatId, storageRef, metadata | Adjunto de una conversación |
| Campaign | id, accountId, chatSessionId, title, mandate, criteria, maxApplications, status, statusReason, timestamps | Agrupa candidaturas |
| Application | id, accountId, campaignId, companyName, jobTitle, jobUrl, platform, location, status, statusReason, documentRefs, submittedAt, timestamps | Pertenece a una campaña y conserva referencias documentales |
| WorkspaceController | accountId, instanceId | Controla una cuenta |
| Wallet | accountId, environment, balance | Acceso comercial |
| TopUp | id, package, nominal, remaining, purchasedAt, expiresAt | Recarga de créditos |
| LedgerEntry | accountId, key, kind, amount, details, at | Registro contable |

### 7.3. Relational Mapping

Los esquemas de referencia se organizan en PostgreSQL:

**users**
- candidate_profiles
- job_preferences
- cv_documents
- original_documents
- document_cleanup
- campaigns
- applications
- account_controllers
- queued_chat_attachments

**billing**
- wallets
- topups
- ledger

**catalog**
- geo_countries

**neon_auth**
- user
- session

En CVs, revision es un token de concurrencia y no existe una entidad de snapshots históricos. applications.document_refs almacena identificadores y tipo de documento; no guarda revision, perfil JSON ni bytes del archivo. resultsRepository resuelve ownership y nombre contra la biblioteca actual al registrar y consultar el detalle.

### 7.4. Data Ownership & Constraints

- Toda entidad de usuario lleva accountId o una relación inequívoca con su propietario.
- Las consultas se filtran por ownership antes de devolver datos.
- Las claves de almacenamiento se aíslan por cuenta.
- Una candidatura referencia una campaña de la misma cuenta.
- Las referencias documentales se resuelven contra los CV u originales que pertenecen a la cuenta; no conservan un snapshot histórico.
- La identidad determinista de candidatura opera dentro de una campaña; no existe deduplicación global ni historial separado de intentos.
- Las transiciones de campaña utilizan compare-and-set por estado; la asociación al chat es lógica, no una FK a Vertex AI.
- Las restricciones de integridad deben residir en schemas y base de datos cuando corresponda.

## 8. Persistence & Consistency

### 8.1. PostgreSQL

Neon PostgreSQL es la fuente de verdad para perfiles, preferencias, CV metadata, campañas, candidaturas, control y billing. Drizzle ORM define el acceso tipado; el driver pg gestiona conexiones.

Las operaciones que modifican recursos relacionados deben utilizar transacciones. Las restricciones, índices y claves compuestas deben reforzar ownership y consistencia, no depender solo de validaciones de frontend.

### 8.2. Object Storage

Los originales y archivos privados se guardan en almacenamiento compatible con S3. Las claves incluyen un prefijo derivado de la cuenta; cada lectura, escritura, acceso firmado y eliminación valida ownership.

Los enlaces firmados tienen duración limitada. Los archivos temporales pasan por un proceso de adopción o limpieza para evitar objetos huérfanos.

### 8.3. Agent Sessions

El historial conversacional utiliza sesiones administradas por Vertex AI Agent Engine. La API conserva las referencias y los metadatos que necesita el producto. Los adjuntos y sus referencias se gestionan mediante almacenamiento privado y registros asociados a la cuenta.

### 8.4. External Effects

El envío al portal y la escritura en PostgreSQL son operaciones distintas. ResultsRepository registra el resultado observado por el agente mediante upsert por ID estable. Conserva estado, motivo, URL, fechas y referencias documentales, no artefactos de evidencia ni un registro separado de intentos.

El presupuesto cuenta confirmed, unconfirmed y cualquier fila con submittedAt; se calcula después del registro, sin reserva previa al envío. confirmed no se degrada y la primera fecha de envío se conserva. Los resultados inciertos se reconcilian antes de repetir acciones externas.

La consulta GET /v1/dashboard recupera campañas running sin ejecución activa como stopped o completed según presupuesto. [Campañas — Técnico](campaigns/technical.md) y [Postulaciones — Técnico](applications/technical.md) definen las garantías concretas.

## 9. API & Realtime Contracts

### 9.1. REST

La API utiliza el prefijo **/v1**. Las áreas principales son:

| Área | Recursos |
|---|---|
| Auth / Account | Verificación de identidad y eliminación |
| Profiles | Perfil, preferencias e importación |
| CVs | Originales, biblioteca, detalle, edición, selección y descarga |
| Chats | Conversaciones, mensajes, historial y adjuntos |
| Applications | Dashboard, listado y detalle |
| Campaigns | Consulta de campañas |
| Billing | Wallet, checkout, movimientos y webhooks |

Campaigns y Applications exponen únicamente consultas REST. Las escrituras se realizan mediante herramientas de dominio del agente. GET /v1/dashboard también recupera campañas interrumpidas.

Los contratos de request, response, parámetros, eventos y errores se centralizan en **packages/contracts** y se validan en los límites de entrada.

### 9.2. Workspace WebSocket

**Ruta:** **/v1/workspace**

El protocolo diferencia mensajes de cliente, mensajes de servidor, frames de extensión, eventos de navegador y respuestas a comandos. Cada comando correlaciona requestId y resultado. Los frames se validan y limitan por tamaño.

El canal soporta conexión, autenticación, heartbeat, control, transferencia, comandos de navegador, eventos y recuperación.

### 9.3. Chat Streaming

Los eventos del agente se normalizan antes de llegar a la interfaz. El cliente debe distinguir mensajes, pasos de ejecución, resultados, preguntas al candidato, errores, pausa y finalización. No debe interpretar texto libre del modelo como un cambio de estado de dominio.

### 9.4. Error Contract

Los errores deben utilizar códigos estables y mensajes seguros. La interfaz transforma códigos en instrucciones accionables. Los errores de proveedor no deben exponer tokens, secretos, cookies, datos personales ni trazas internas.

## 10. UX/UI Architecture

### 10.1. Information Architecture

La navegación principal contiene cinco áreas:

1. Chat.
2. Dashboard.
3. Postulaciones.
4. Biblioteca de CV.
5. Perfil profesional.

El chat es el espacio principal de instrucción y ejecución. Dashboard y Postulaciones presentan resultados estructurados. Biblioteca y Perfil administran la información que el agente utiliza.

### 10.2. Chat & Browser Activity

Chat integra conversación, actividad del agente, CampaignSummary y compositor. Los eventos browser_*, openBrowser y prepareAttachment omiten argumentos y resultados; la transcripción muestra el nombre de la herramienta. El Chrome local conserva las pestañas reales; no existe viewport integrado ni modo Operator. Stop y Resume se realizan desde Chat; Dashboard y Applications consultan resultados.

## 11. Security Architecture & Threat Model

| Amenaza | Control arquitectónico |
|---|---|
| Acceso cruzado entre cuentas | Ownership por accountId, filtros obligatorios y pruebas negativas |
| JWT inválido o sesión revocada | Validación JWKS, claims y sesión activa |
| Robo de secretos | Secretos solo en backend y gestor de secretos del entorno |
| Prompt injection desde portales o correo | Contenido externo no confiable; herramientas limitadas por scope |
| Envío sin autorización | Mandato e instrucciones del agente; no existe gate semántico por comando de navegador |
| Automatización prohibida por el portal | Política del agente; sin matriz de fuentes aplicada por el runtime |
| Resultado incierto tras timeout | ID determinista por campaña y reconciliación por observación del portal |
| Exposición de CV | Storage privado, ownership y URLs firmadas de corta duración |
| Control concurrente del navegador | instance_id por cuenta, advisory locks y transferencia explícita |
| Exposición en logs | Eventos estructurados y minimización de datos sensibles |
| Eliminación incompleta de cuenta | Coordinación de DB, sesiones, storage, billing y recursos externos |
| Comunicación no autorizada | allow_communication en contexto y prompt; no gate semántico por acción |

### 11.1. Authorization Boundaries

- **Account scope:** define qué recursos puede leer o modificar el candidato.
- **Campaign scope:** identifica campaña, chat, mandato, criterios y límite.
- **Communication scope:** allow_communication informa al agente sobre la autorización de comunicaciones.
- **Browser scope:** define qué navegador y pestañas puede controlar la instancia autorizada.
- **Tool scope:** define qué operaciones puede invocar el agente en el turno actual.

El servidor valida identidad, ownership y estado de escrituras. La interpretación del mandato y la política de comunicación depende del agente; los comandos genéricos de navegador no verifican semánticamente cada acción.

## 12. Reliability, Performance & Cost

### 12.1. Reliability

- Persistir resultados confirmados antes de continuar.
- Separar estado de campaña, estado de candidatura y estado de conexión.
- Recuperar checkpoints y reconciliar operaciones externas.
- Evitar reintentos automáticos cuando el envío sea incierto.
- Cancelar las ejecuciones ante pérdida del WebSocket; cerrar solo la pestaña Mirai no equivale a Stop.
- Hacer idempotentes las operaciones de dominio que puedan repetirse.

### 12.2. Performance

La latencia de Mirai tiene componentes distintos: UI/API, inferencia, navegación, espera del portal y almacenamiento. Las métricas deben atribuirse a cada componente; no se debe responsabilizar al backend por tiempos de terceros.

### 12.3. Cost Management

Billing registra operaciones de inferencia por tipo, modelo, región, uso y tarifa aplicable. La wallet y el ledger son la fuente contable. El Dashboard actual no agrega costo por campaña ni por candidatura.

## 13. Infrastructure & Deployment

### 13.1. Runtime

- **Web:** servicio Next.js independiente.
- **API:** servicio Express independiente, con HTTP y Workspace WebSocket.
- **Extension:** paquete distribuible para el navegador de escritorio.
- **Database:** Neon PostgreSQL.
- **Object Storage:** almacenamiento privado compatible con S3.
- **Agent:** Google ADK / Vertex AI Agent Engine.
- **Inference:** Google GenAI en Vertex AI.
- **Payments:** Paddle.

### 13.2. Build & Deployment

Los servicios Web y API utilizan Dockerfiles independientes y Cloud Build para construir imágenes. La infraestructura de ejecución utiliza Cloud Run. Las migraciones de PostgreSQL se administran desde el paquete API con Drizzle Kit.

Los despliegues deben preservar compatibilidad entre contratos, migraciones, web, API y extensión. La extensión requiere distribución y actualización separadas de los servicios Cloud Run.

### 13.3. Configuration

La configuración se entrega mediante variables de entorno y secretos del entorno:

- Database: DATABASE_URL y conexión directa cuando se requiera.
- Identity: NEON_AUTH_BASE_URL.
- Web/API origins: WEB_ORIGIN y NEXT_PUBLIC_API_ORIGIN.
- Agent Engine: GOOGLE_ADK_AGENT_ENGINE, GOOGLE_ADK_MODEL y GOOGLE_ADK_SESSION_TTL.
- Inference: GOOGLE_CLOUD_PROJECT, GOOGLE_CLOUD_LOCATION y GOOGLE_GENAI_MODEL.
- Storage: AWS_REGION, AWS_ENDPOINT_URL_S3 y NEON_STORAGE_BUCKET.
- Billing: BILLING_ENVIRONMENT y configuración Paddle por entorno.

Los valores sensibles no se versionan en el repositorio.

## 15. Technical Constraints & Open Design Decisions

1. La compatibilidad por portal depende de la estructura del sitio y de sus condiciones de uso.
2. La ejecución local requiere navegador y extensión disponibles; el cierre del equipo detiene la actividad del navegador.
3. Las sesiones externas pueden caducar y exigir autenticación del candidato.
4. CAPTCHA, verificaciones personales y controles antiabuso no se consideran bypassables por diseño.
5. Los tokens revision de CV detectan escrituras concurrentes; no conservan snapshots históricos.
6. El resultado de envío depende de la observación del agente; no existe almacén de evidencia externa.
7. La compatibilidad de Firefox requiere un contrato de navegador equivalente.
8. Los plazos de retención, transferencias internacionales y derechos del titular se detallan en Security & Privacy / Data Lifecycle.
9. La política de costos y precios se detalla en Billing.
10. Los límites operativos y objetivos de disponibilidad se concretan en Observability & Reliability.
