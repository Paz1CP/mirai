# PRD — Product Requirements Document

## 1. Problema, usuarios y resultado esperado

**Problema.** Una persona que busca empleo en canales digitales debe localizar ofertas dispersas, distinguir las pertinentes, adaptar documentos, rellenar formularios heterogéneos, enviar candidaturas y administrar respuestas. La repetición consume tiempo y dificulta sostener la búsqueda.

**Usuario y cliente.** Candidato individual que busca empleo mediante interfaces digitales en Latinoamérica, incluido Brasil: cualquier profesión o seniority; empleos presenciales, híbridos y remotos. El sistema no requiere que el candidato sepa configurar agentes o escribir prompts.

**Resultado controlado por el software.** Encontrar oportunidades alineadas, enviar candidaturas comprobables y sostener comunicaciones operativas con la menor intervención necesaria. Conseguir entrevistas, ofertas o contratación depende de terceros y **no** es una condición de éxito de una postulación técnica.

**Operación local [D].** Mirai es una aplicación web con extensión para navegadores Chromium y Firefox de escritorio. El agente trabaja en pestañas propias mientras el candidato usa otras aplicaciones; la pestaña controladora de Mirai debe permanecer abierta. Al cerrarla, se pausa la campaña y la reanudación requiere acción explícita. Si se pierde conectividad o el equipo se suspende, se conserva y reconcilia el trabajo antes de continuar de forma segura. No se requieren navegadores cloud por sesión ni actividad con el dispositivo apagado.

## 2. Alcance y expectativas

| Incluido en MVP | Excluido del MVP |
|---|---|
| Perfil profesional, CV, preferencias y restricciones obligatorias | Bolsa de empleo propia, catálogo público de vacantes |
| Campaña autónoma de descubrimiento y postulación en múltiples sitios | Coaching, cursos, mejora de carrera, simulador de entrevistas |
| Operación de UIs reales mediante extensión de escritorio | Dependencia funcional de APIs de portales de empleo |
| Adaptación documental y respuestas basadas en datos declarados | Inventar experiencia, títulos, certificados o respuestas biográficas |
| Seguimiento de candidaturas y registro de evidencia | Indicadores decorativos de «98 % de match», gamificación |
| Comunicación autorizada con contactos profesionales por plataformas laborales o correo, incluido Gmail | Bandeja propia de reclutadores o sistema paralelo de mensajería; participar en entrevistas, grabar audio/video personal, rendir exámenes |
| Pendientes para datos ausentes y pasos personales | Garantizar acceso irrestricto a cualquier plataforma o contratación |
| Configuración, pausa, reanudación, control de acceso y cobro | Modelo LLM, proveedor de pagos o precio definitivamente fijados |

**Principios de comportamiento [D]:**

1. **Las oportunidades alineadas que se descubran** se consideran para postulación dentro de los límites definidos por el candidato; no existe un cupo arbitrario como regla del producto. «Todas» no significa que el software tenga omnisciencia del mercado ni que deba postular a vacantes incompatibles.
2. **Autonomía completa por defecto**, una vez que el candidato configure su perfil y autorice la campaña. Puede reducir la autonomía, editar preferencias, pausar o cancelar.
3. **Criterios obligatorios definidos por el usuario** (por ejemplo: salario mínimo, país, ubicación, modalidad, tipo de contrato, elegibilidad). El agente interpreta la pertinencia profesional solo dentro de esos límites.
4. Si una respuesta exige un hecho personal no proporcionado ni legitimamente derivable, la candidatura queda **pendiente de revisión** y el agente continúa trabajando en otras.
5. La información declarada por el usuario es la fuente operativa; el sistema no investiga si la trayectoria declarada es verdadera ni crea credenciales por iniciativa propia.
6. Mirai puede contactar y responder a reclutadores, directivos y otros contactos profesionales únicamente en plataformas laborales o por correo, incluido Gmail. Una autorización previa cubre comunicaciones posteriores dentro de su alcance hasta su revocación; no se pide permiso para cada mensaje.
7. Los desafíos de acceso se intentan atender cuando la tecnología y el acceso lo permiten; un obstáculo no resuelto nunca se reporta como postulación exitosa.

## 3. Actores y límites

| Actor | Rol |
|---|---|
| **Candidato** | Titular del perfil, configura restricciones, autoriza acciones, atiende pendientes y recibe resultados |
| **Agente** | Descubre, decide pertinencia, navega, prepara respuestas, ejecuta y verifica acciones autorizadas |
| **Extensión de navegador** | Ejecuta las acciones en el navegador local, administra sus pestañas y comunica resultados |
| **Portal / ATS / empresa** | Publica ofertas, provee formularios, confirma o rechaza solicitudes |
| **Reclutador** | Recibe y envía mensajes, solicita pasos adicionales |
| **Gmail** | Canal externo de comunicaciones del candidato |
| **Proveedor de inferencia** | Ofrece el modelo que interpreta contexto y decide acciones; se selecciona en desarrollo |
| **Operador del producto** | Mantiene servicio, controla costos, fallos y soporte con accesos segregados |

## 4. Recorrido principal de producto

```text
Crear cuenta y habilitar servicio
  -> proporcionar CV, hechos profesionales y preferencias obligatorias
  -> instalar/conectar la extensión y autorizar sitios/cuentas necesarios
  -> indicar en lenguaje natural fuentes, límites y preferencias; autorizar campaña autónoma
  -> descubrir vacantes -> comprobar restricciones y pertinencia
  -> descartar incompatibles y duplicadas
  -> preparar CV/carta/respuestas -> operar UI y enviar
  -> verificar resultado -> registrar evidencia
  -> revisar Gmail y mensajería autorizada -> responder lo rutinario
  -> derivar pendientes personales -> continuar la campaña
  -> notificar al finalizar y presentar reporte de resultados, descartes y pendientes
  -> pausar/reanudar/cancelar por decisión del candidato
```

El agente **no toma el control de la pestaña activa del usuario** como comportamiento normal. Los detalles de pestañas, permisos y concurrencia se diseñarán después.

## 5. Resultados medibles del MVP

| Indicador | Definición | Por qué existe |
|---|---|---|
| Postulación confirmada | Envío con confirmación observable y evidencia asociada | Evitar contar clics como éxitos |
| Precisión de elegibilidad | Postulaciones enviadas sin violar restricciones obligatorias | Evitar volumen inútil |
| Intervención humana | Pendientes y minutos de usuario por candidatura confirmada | Medir autonomía real |
| Continuidad | Trabajos recuperados sin duplicaciones tras interrupciones | Validar ejecución local |
| Cobertura efectiva | Sitios y flujos probados con envíos confirmados | Medir compatibilidad real |
| Costo por resultado | Inferencia + operación atribuible / postulaciones confirmadas | Habilitar pricing posterior |

No se establece una cuota de candidaturas diarias ni un precio sin datos experimentales. Los objetivos mínimos de aceptación de software figuran en las secciones 7 y 11.

# SRS — Software Requirements Specification

## 6. Requisitos funcionales (Functional Requirements Specification)

Todos los requisitos usan **«El sistema deberá...»** e indican resultados observables. El carácter transversal de los portales no supone integración garantizada con todos los sitios del mundo.

### 6.1. Cuenta, perfil y consentimiento

| ID | Requisito funcional |
|---|---|
| **FR-01** | Permitir al candidato crear cuenta, autenticarse y cerrar sesión. |
| **FR-02** | Permitir cargar y consultar el CV original, conservarlo inmutable y extraer información profesional revisable; toda modificación parte de una copia. |
| **FR-03** | Registrar y editar hechos proporcionados por el candidato: experiencia, educación, habilidades, idiomas, contactos y otras respuestas reutilizables. |
| **FR-04** | Registrar restricciones obligatorias y preferencias de búsqueda: ubicaciones, modalidades, salario mínimo cuando se defina, tipos de contrato, elegibilidad y exclusiones. |
| **FR-05** | Distinguir restricciones **obligatorias** de preferencias **flexibles**, sin exigir un porcentaje público de compatibilidad. |
| **FR-06** | Permitir instalar/vincular la extensión en Chromium o Firefox de escritorio y detectar si está conectada, desconectada o sin permisos necesarios. |
| **FR-07** | Solicitar y registrar autorización expresa para actuar en los sitios/cuentas seleccionados, presentar candidaturas y comunicarse; una autorización de comunicaciones cubre acciones posteriores dentro de su alcance hasta ser revocada. |
| **FR-08** | Permitir editar o revocar autorizaciones y gestionar el nivel de autonomía sin volver a configurar el perfil completo. |

### 6.2. Campaña y descubrimiento

| ID | Requisito funcional |
|---|---|
| **FR-09** | Permitir iniciar, pausar, reanudar y finalizar una campaña de búsqueda. |
| **FR-10** | Ejecutar búsqueda recurrente en los sitios accesibles autorizados por el candidato; puede limitarse a uno o abarcar varios según su instrucción. |
| **FR-11** | Extraer los datos disponibles de cada vacante necesarios para evaluarla y ejecutar su postulación. |
| **FR-12** | Excluir oportunidades que contradigan una restricción obligatoria conocida; si falta información indispensable para decidir, no enviar automáticamente. |
| **FR-13** | Evaluar pertinencia profesional usando CV, experiencia, habilidades y preferencias; avanzar con las ofertas encontradas que resulten alineadas dentro de los límites del candidato. |
| **FR-14** | Reconocer solicitudes ya enviadas o en curso y evitar iniciar postulaciones duplicadas para la misma vacante/candidato. |
| **FR-15** | Conservar referencia del anuncio, empresa, rol y URL de origen para trazabilidad, sin ofrecer un marketplace de empleo. |

### 6.3. Preparación y envío autónomos

| ID | Requisito funcional |
|---|---|
| **FR-16** | Seleccionar o adaptar una variante reutilizable del CV para la vacante usando solo información declarada; conservar el vínculo con el perfil y la versión utilizada. |
| **FR-17** | Generar carta de presentación y respuestas libres cuando el formulario las requiera y exista fundamento suficiente en el perfil. |
| **FR-18** | Completar campos, seleccionar opciones, adjuntar documentos, navegar pasos y activar el envío mediante la **interfaz web real** del destino. |
| **FR-19** | Gestionar cuentas y sesiones existentes del candidato, solicitando su intervención cuando un paso de autenticación no pueda completarse de forma autorizada. |
| **FR-20** | Identificar desafíos, errores y comprobaciones del sitio, intentar resolución mediante interacciones permitidas y derivar a pendiente los irresolubles. |

| ID | Requisito funcional |

No se exige implementar ambos.

## 7. Requisitos no funcionales (ISO/IEC 25010:2023)

La norma ISO/IEC 25010:2023 clasifica la calidad del producto en **nueve características**. Aquí se materializan como condiciones de aceptación propias del producto; **los valores [T] son objetivos propuestos para pruebas**, no cifras demostradas ni promesas de compatibilidad universal.

| ID | Característica ISO/IEC 25010:2023 | Requisito medible / método de validación |
|---|---|---|
| **NFR-01** | **Adecuación funcional** (*Functional suitability*) | En la suite de aceptación, **100 % de casos críticos** de no duplicación, exclusión por filtros obligatorios, no invención, pausa y clasificación honesta del envío deberán aprobarse. |
| **NFR-02** | **Eficiencia de rendimiento** (*Performance efficiency*) | **[T]** En entorno de prueba definido, el 95 % de aperturas del panel operativo deberá mostrar contenido inicial en ≤3 s, excluyendo el tiempo de terceros. |
| **NFR-03** | Eficiencia de rendimiento | Registrar duración y consumo de recursos de cada postulación; **[T]** la extensión no deberá bloquear perceptiblemente la pestaña activa en la suite de coexistencia. CPU/RAM máximas se fijarán tras perfilar equipos de referencia. |
| **NFR-04** | **Compatibilidad** (*Compatibility*) | Las funciones críticas web + extensión deberán pasar pruebas en navegadores Chromium y Firefox de escritorio soportados; el navegador del usuario y sus pestañas preexistentes deberán seguir operativos. |
| **NFR-05** | Compatibilidad | Verificar E2E los portales de una **matriz de compatibilidad versionada** con ofertas de prueba reales o entornos autorizados; cada sitio tendrá resultado «compatible», «parcial» o «no compatible» y fecha de prueba. No se inventa cobertura global. |
| **NFR-06** | **Capacidad de interacción** (*Interaction capability*) | **[T]** Un candidato de prueba deberá completar perfil, extensión, permisos e inicio de campaña siguiendo instrucciones en pantalla mediante lenguaje natural sin conocimientos técnicos ni prompts maestros. |
| **NFR-07** | Capacidad de interacción | Los estados «confirmado», «no confirmado», «pendiente» y «fallido» deberán distinguirse por texto y descripción, no depender solo del color; objetivo de accesibilidad: WCAG 2.2 AA para las vistas propias. |
| **NFR-08** | **Fiabilidad** (*Reliability*) | En pruebas de cierre de pestaña web, suspensión, reinicio de extensión y pérdida de conexión, la tarea deberá recuperarse o declararse pendiente **sin pérdida de registros confirmados ni duplicar envíos**. |
| **NFR-09** | Fiabilidad | **[T]** Ninguna operación externa crítica debe marcarse confirmada sin señal verificable del destino; ante incertidumbre debe conservar estado «no confirmado» o «pendiente». |
| **NFR-10** | **Seguridad** (*Security*) | La extensión y backend solo podrán actuar con identidad y permisos vigentes; pruebas negativas deberán demostrar que un usuario no accede a CV, mensajes ni sesiones de otro. |
| **NFR-11** | Seguridad | Datos personales y tokens bajo transporte cifrado; secretos de proveedores **nunca** embebidos en frontend/extensión; permisos externos revocables; logs sin credenciales, cookies ni contenido sensible completo por defecto. |
| **NFR-12** | Seguridad | Las páginas externas, ofertas y correos son **datos no confiables**: instrucciones incrustadas allí no deben cambiar el mandato del candidato, elevar permisos ni provocar filtraciones. Prueba mediante casos de *prompt injection*. |
| **NFR-13** | Seguridad | Separar comunicaciones laborales autorizadas de mensajes ajenos a la campaña; registrar qué cuenta/canal realizó cada envío y ofrecer revocación efectiva. |
| **NFR-14** | **Mantenibilidad** (*Maintainability*) | Reglas de elegibilidad, estado, verificación de resultado y navegador deberán tener pruebas automatizadas independientes del proveedor LLM y del portal concreto. |
| **NFR-15** | Mantenibilidad | Cambiar el proveedor/modelo de inferencia no deberá obligar a modificar reglas de negocio ni los criterios de aceptación de postulación. |
| **NFR-16** | **Flexibilidad** (*Flexibility*) | Soportar incorporación de nuevas fuentes/sitios y actualización de interacciones sin modificar datos de perfiles existentes; comprobarlo en prueba de regresión. |
| **NFR-17** | Flexibilidad | No asumir una única geografía, idioma de oferta o modalidad; validar perfiles y oportunidades en español y portugués, incluida terminología brasileña, con ejemplos representativos. |
| **NFR-18** | **Seguridad operacional** (*Safety*) | Una falla, incertidumbre o recuperación no podrá disparar envíos repetidos, comunicaciones duplicadas, aceptación de contratos ni acciones personales irreversibles sin una autorización aplicable. |
| **NFR-19** | Seguridad operacional | Antes de una acción externa irreversible, validar autorización y restricciones vigentes; al detectar revocación o pausa, impedir **nuevas** acciones (una operación ya enviada no puede deshacerse). |
| **NFR-20** | Fiabilidad / rendimiento | Medir por campaña: pasos y tokens del modelo, fallos, intentos, confirmaciones y costo. Las mediciones usarán una muestra reproducible; sin medición, no se fija tiempo máximo de postulación sobre portales ajenos. |

**Criterios de entorno de pruebas [T]:** Chrome estable en Windows como referencia inicial de desarrollo; validar adicionalmente macOS y Linux antes de prometer compatibilidad comercial con ellos. Dispositivos móviles no ejecutan este agente local en el MVP. La web puede consultarse en otros dispositivos si se implementa, pero **ejecutar** requiere un navegador Chromium o Firefox de escritorio con extensión disponible.

## 8. Reglas de negocio (Business Rules Specification)

Las reglas siguientes son invariantes de dominio y de autorización, **no algoritmos ni decisiones de stack**.

| ID | Regla |
|---|---|
| **BR-01** | Una campaña pertenece a un único candidato autenticado y opera bajo sus datos y autorizaciones. |
| **BR-02** | Ninguna campaña puede actuar externamente sin autorización vigente; su autonomía es completa por defecto **después** de ser autorizada. |
| **BR-03** | Una vacante que contradiga cualquier restricción obligatoria conocida **no es elegible**. |
| **BR-04** | La pertinencia profesional debe fundarse en datos declarados y requisitos de la vacante, no en una cifra decorativa de compatibilidad. |
| **BR-05** | Las ofertas elegibles se procesan dentro de las fuentes y del máximo indicado por el candidato; no se impone un cupo arbitrario del producto. |
| **BR-06** | Una misma candidatura/candidato/destino no puede enviarse dos veces por reintento o recuperación automática. |
| **BR-07** | El sistema puede reformular o reorganizar hechos declarados, pero no **introducir hechos biográficos, credenciales o experiencia no proporcionados**. |
| **BR-08** | La plataforma utiliza el contenido declarado por el candidato como fuente operativa; no establece por cuenta propia su veracidad. |
| **BR-09** | Si falta un dato imprescindible, la candidatura pasa a **pendiente de revisión** y no bloquea el procesamiento de las demás. |
| **BR-10** | Si la evidencia no permite conocer el estado final de un envío, este no cuenta como postulación confirmada. |
| **BR-11** | Una candidatura confirmada conserva su registro y evidencia aunque después sea rechazada por la empresa. |
| **BR-12** | Una acción personal indelegable (entrevista, video/voz personal, prueba presencial, verificación exclusiva del titular, aceptación contractual) se deriva al candidato y registra su enlace. |
| **BR-13** | Las conversaciones rutinarias podrán atenderse automáticamente en los canales autorizados y con base en datos del candidato; decisiones personales no autorizadas pasan a revisión. |
| **BR-14** | El agente no inicia nuevas acciones externas si el candidato pausó, terminó o revocó su campaña. |
| **BR-15** | Cerrar la pestaña controladora pausa la campaña; la pérdida de conectividad o del ejecutor detiene acciones hasta una recuperación segura. Una campaña pausada requiere reanudación explícita. |
| **BR-16** | La condición comercial de acceso pagado se comprobará antes de activar campañas de producción; precio y plan aún no están decididos. |
| **BR-17** | Una oferta puede registrarse como dato operativo de candidatura; ello no convierte al producto en una bolsa de vacantes para terceros. |
| **BR-18** | Las restricciones y permisos más recientes del candidato prevalecen para **acciones futuras**; registros históricos no se reescriben. |
| **BR-19** | Una restricción crítica desconocida o un requisito imprescindible de elegibilidad no verificable impiden el envío autónomo de esa vacante hasta aclaración. |
| **BR-20** | La autorización del candidato no anula los controles de acceso del sitio de destino. Si el flujo no puede completarse, se registra el resultado y continúa la campaña. |
| **BR-21** | Una sola instancia de Mirai controla la cuenta; la transferencia invalida el control anterior y no autoriza acciones concurrentes incompatibles. |
| **BR-22** | Los CV originales son inmutables; originales, variantes y sus versiones se conservan sin caducidad automática hasta que el candidato solicite su eliminación. |
| **BR-23** | El máximo de postulaciones indicado por el candidato es vinculante; un resultado incierto ocupa una reserva hasta reconciliarse para evitar superar el máximo. |

### 8.1. Semántica mínima de resultados

| Resultado | Cuándo usarlo | Cuenta como enviado |
|---|---|---|
| `confirmed` | Evidencia visible de recepción/solicitud registrada en destino | **Sí** |
| `unconfirmed` | Hubo intento o envío posible, pero recepción no demostrable | No |
| `pending_review` | Falta información, autorización, presencia personal o resolución de incidente | No |
| `failed` | Destino rechazó la operación o se produjo error terminal conocido | No |
| `skipped` | Vacante incompatible, excluida o duplicada | No |

Estas categorías representan **resultados del trabajo**, no un modelo completo de estados de base de datos. El diseño detallado de estados corresponde a la etapa 03.

## 9. Especificaciones de casos de uso — ECU (Use-Case Specifications)

Se detallan los casos con más riesgo, bifurcaciones y valor observable. Flujos evidentes de cuenta, perfil y consulta quedan cubiertos mediante `FR` y `US`; no se multiplican diagramas por ceremonia.

### UC-01 — Preparar y autorizar campaña

- **Actor principal:** candidato.
- **Precondiciones:** cuenta accesible; navegador de escritorio compatible y extensión disponibles para ejecutar.
- **Disparador:** el candidato solicita iniciar campaña.
- **Flujo principal:** (1) carga CV; (2) revisa/corrige hechos; (3) expresa en lenguaje natural fuentes, filtros, límites y preferencias; (4) vincula extensión; (5) concede autorizaciones; (6) habilita servicio y comienza campaña; (7) sistema muestra estado activo.
- **Alternativas:** si falta CV o filtro imprescindible, se solicita completar; si extensión no está lista, se muestra acción para habilitarla; si no hay acceso pagado comercial, se presenta habilitación de servicio según plan vigente.
- **Excepciones:** consentimiento revocado, error de archivo o cuenta inválida: no iniciar navegación.
- **Postcondiciones:** campaña activa con mandato verificable o solicitud sin activar y motivo visible.
- **Referencias:** FR-01–09, FR-42–43; BR-01–02, BR-16.

### UC-02 — Descubrir y evaluar vacantes

- **Actor principal:** agente; **actor externo:** portal.
- **Precondiciones:** campaña activa, navegador disponible, perfil y restricciones guardados.
- **Flujo principal:** (1) consultar fuentes web; (2) obtener detalles de ofertas; (3) aplicar filtros obligatorios; (4) evaluar pertinencia profesional; (5) comprobar duplicados; (6) encolar ofertas elegibles.
- **Alternativas:** oferta incompatible → `skipped`; oferta ya aplicada → `skipped`; dato crítico ausente → `pending_review` si impide determinar elegibilidad; resultado irrelevante → descartado.
- **Excepciones:** fuente inaccesible → registrar incidencia de fuente y seguir con otras.
- **Postcondiciones:** trabajo preparado y vacantes inelegibles justificadas; ningún envío ocurre aquí.
- **Referencias:** FR-10–15; BR-03–06, BR-19–20.

### UC-03 — Preparar y enviar candidatura

- **Actor principal:** agente; **actor externo:** sitio de empleo.
- **Precondiciones:** vacante elegible, no duplicada, campaña autorizada, navegador disponible.
- **Flujo principal:** (1) consultar perfil y oferta; (2) seleccionar o adaptar variante reutilizable del CV y preparar carta; (3) abrir formulario; (4) responder preguntas conocidas; (5) subir archivos; (6) revisar campos y autorización vigente; (7) enviar; (8) obtener señal de recepción; (9) guardar `confirmed` y evidencia.
- **Alternativas:** campos opcionales innecesarios → omitir donde admita el sitio; flujo multipaso → continuar; portal informa rechazo → `failed`; estado de recepción ambiguo → `unconfirmed`.
- **Excepciones:** pérdida de conexión → recuperación de UC-06; dato indispensable desconocido → UC-04; paso personal → UC-04.
- **Postcondiciones:** registro trazable con resultado correcto; cero dobles envíos automáticos.
- **Referencias:** FR-16–25; BR-06–12.

### UC-04 — Derivar información o intervención personal

- **Actor principal:** agente; **actor secundario:** candidato.
- **Precondiciones:** candidatura/comunicación requiere dato no disponible o participación humana.
- **Flujo principal:** (1) detener solo la tarea afectada; (2) guardar progreso y sitio; (3) registrar motivo concreto, URL y acción pendiente; (4) notificar al candidato; (5) continuar otras tareas; (6) tras respuesta del candidato, comprobar condiciones y reanudar.
- **Alternativas:** el candidato decide omitir la oportunidad → `skipped`; completa la acción directamente en el portal → se reconcilia el estado observado; si sigue faltando información, permanece pendiente.
- **Excepciones:** caducidad del formulario → reiniciar el flujo solo después de comprobar que no se envió antes.
- **Postcondiciones:** pendiente resoluble, nunca una postulación falsa ni bloqueo global.
- **Referencias:** FR-21–22, FR-34–35; BR-09, BR-12, BR-19.

### UC-05 — Gestionar comunicaciones laborales

- **Actor principal:** agente; **actores externos:** Gmail, bandejas de portales, reclutador.
- **Precondiciones:** canal vinculado y autorizado, campaña o seguimiento vigente.
- **Flujo principal:** (1) consultar mensajes pertinentes en el portal o correo autorizado; (2) determinar si cabe responder; (3) preparar una respuesta fundamentada; (4) enviarla en ese mismo canal; (5) conservar solo el estado operativo necesario para evitar duplicados.
- **Alternativas:** consulta no rutinaria o dato ausente → UC-04; invitación a entrevista → notificar y derivar la participación personal necesaria; mensaje irrelevante → no modificarlo ni contestarlo.
- **Excepciones:** Gmail sin permiso o sesión caducada → pendiente de reconexión y continuar por otros canales disponibles.
- **Postcondiciones:** comunicación realizada en el canal autorizado, sin respuestas duplicadas ni historial paralelo de conversación.
- **Referencias:** FR-26–32; BR-07–08, BR-13.

### UC-06 — Recuperar ejecución local

- **Actor principal:** extensión/sistema.
- **Precondiciones:** trabajo en progreso o pendiente, con estado previo persistido.
- **Disparador:** cierre de pestaña web, suspensión, cierre/reinicio de Chrome, caída de conexión o reinicio de extensión.
- **Flujo principal:** (1) detectar disponibilidad recuperada; (2) obtener estado persistido y autorizaciones actuales; (3) reconciliar acciones que pudieron completarse; (4) tras reanudación explícita si está pausada, continuar únicamente las tareas no concluidas; (5) reflejar el estado al usuario.
- **Alternativas:** campaña pausada/revocada → no reanudar; envío incierto → `unconfirmed`/revisión antes de un posible nuevo intento; acceso externo expirado → pendiente de autenticación.
- **Excepciones:** datos de recuperación inconsistentes → conservar evidencia, bloquear reenvío automático y registrar incidencia.
- **Postcondiciones:** continuidad segura sin perder confirmaciones ni duplicar acciones.
- **Referencias:** FR-25, FR-37–40; BR-06, BR-14–15, BR-18.

### UC-07 — Consultar resultados y resolver pendientes

- **Actor principal:** candidato.
- **Precondiciones:** cuenta con actividad registrada.
- **Flujo principal:** (1) abrir panel; (2) ver total confirmado e incidencias por estado; (3) abrir candidatura con URL/evidencia; (4) revisar pendiente; (5) aportar dato o marcar acción personal realizada; (6) solicitar reanudación de tarea.
- **Alternativas:** no hay actividad → vista vacía con estado real; evidencia parcial → mostrar incertidumbre sin convertirla en éxito.
- **Excepciones:** campaña ya revocada → permitir consultar historial autorizado sin reiniciar acciones.
- **Postcondiciones:** candidato conoce actividad y pendientes; registros preservados.
- **Referencias:** FR-23–24, FR-33–36; BR-10–11.

### UC-08 — Cambiar permisos o detener campaña

- **Actor principal:** candidato.
- **Precondiciones:** cuenta autenticada y una campaña existente.
- **Flujo principal:** (1) cambiar filtros, autonomía o permisos; o pausar/finalizar; (2) sistema persiste nueva decisión; (3) agente la aplica antes de la siguiente acción externa; (4) informa resultado.
- **Alternativas:** reanudar campaña → validar servicio, navegador y permisos; solo cambio de filtro → reevaluar trabajo aún no enviado.
- **Excepciones:** una operación ya consumada no puede revertirse; queda en historial.
- **Postcondiciones:** ninguna acción futura vulnera el mandato vigente.
- **Referencias:** FR-04–09, FR-40; BR-14, BR-18.

# 13. Decisiones abiertas para Architecture & Design (etapa 03)

Estas **no son preguntas que bloqueen Requirements**; son decisiones de solución que deben tomarse con prototipos y evidencia:

1. **Modelo de IA:** Gemini 4 Carbon es **candidato**. Comparar con alternativas disponibles usando tasa de finalización, errores, latencia y costo real sobre los mismos casos; **ningún modelo queda fijado aquí**.
2. **Control de Chrome:** decidir combinación de APIs de extensión, aislamiento de pestañas, permisos requeridos y mecanismos para mantener/reanudar actividad pese al ciclo de vida de las extensiones.
3. **Gmail:** elegir integración nativa autorizada o automatización de la UI de Gmail. Ambas son soluciones posibles; el **requisito** es gestionar el canal.
4. **Persistencia:** decidir qué estado vive localmente y cuál se sincroniza, cómo se protegen los datos y cómo se deduplican operaciones externas tras fallos.
5. **Concurrencia:** verificar la exclusividad por cuenta y la serialización de operaciones incompatibles, incluida la transferencia entre instancias.
6. **Matriz de portales:** seleccionar el primer conjunto verificable de sitios según cobertura y condiciones de uso; el alcance conceptual sigue siendo transversal.
7. **UX:** definir los detalles de la interacción conversacional y del panel de actividad y control; dirección visual oscura inspirada en Vercel.
8. **Facturación:** concretar plan, precio y proveedor cuando se disponga de estimaciones de costo y condiciones comerciales. Requisito firme: servicio pagado.
9. **Política de datos:** concretar plazos de retención, localización, borrado y controles por país, preservando privacidad y trazabilidad.

**Consideración técnica ya verificada:** Chrome Manifest V3 puede suspender sus *service workers* cuando están inactivos. Por eso la persistencia/reanudación es una obligación funcional (`FR-39`), no una suposición de que el proceso de la extensión vive para siempre.

# 14. Criterio de cierre de la etapa 02

La especificación queda lista para dar paso a Architecture & Design cuando:

- El MVP esté delimitado sin mezclarlo con un portal de empleo, cursos o acompañamiento profesional (**secciones 1–5**).
- Cada comportamiento externo importante tenga requisito identificable (**FR-01–46**).
- Las nueve características de ISO/IEC 25010:2023 estén consideradas con criterios verificables (**NFR-01–20**).
- Las reglas de elegibilidad, autonomía, no invención, confirmación y recuperación sean explícitas (**BR-01–20**).
- Los escenarios complejos incluyan flujos alternativos, excepciones y postcondiciones (**UC-01–08**).
- Las necesidades del usuario puedan probarse mediante criterios de aceptación y escenarios E2E (**US-01–18, E2E-01–12**).

**Resultado de la etapa:** requisitos y expectativas especificados. **No** se afirma todavía que el software exista, supere pruebas, sea rentable o funcione sobre todos los portales. Eso se demostrará en implementación, verificación y operación.
